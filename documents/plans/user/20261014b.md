# 開発指示書：kaseifu TREC Benchmark

## 1. 目的

Rust製macOSファイル整理ツール `kaseifu` の関連ファイル発見能力を、既存の研究データセットを利用して定量評価する。

対象リポジトリ：

[smapira/kaseifu](https://github.com/smapira/kaseifu?utm_source=chatgpt.com)

### 評価対象

```text
入力ファイル A
    ↓
kaseifu
    ↓
関連ファイル B を1件選択
    ↓
TREC由来の正解集合と比較
    ↓
Hit@1
```

**評価するのは関連ファイルの選択性能であり、フォルダ選択性能ではない。**

ファイルの移動・整理処理は評価対象外とする。

## 2. データセット

使用するデータセット：

**TREC Robust04**

公式情報：

[NIST TREC Robust Track](https://trec.nist.gov/data/robust.html?utm_source=chatgpt.com)

TREC Robust04には、ニュース記事の文書集合、検索トピック、関連性判定（qrels）が存在する。

ただし、**文書コーパスの取得には配布条件やライセンス上の制約がある**。開発開始時に、利用可能な公式配布元、取得権限、データ形式を確認すること。

データが取得できない場合、架空のデータや別のデータセットで代用せず、作業を停止して報告する。

### データの扱い

- 文書本文は改変しない。
- 文書IDと本文の対応を保持する。
- 正解判定には公式qrelsを使用する。
- 文書本文やqrelsをkaseifuの検索ロジックに埋め込まない。
- 元データをGitリポジトリにコミットしない。

## 3. D2D評価データの構築

TRECの公式qrelsは、クエリと文書の関連性を表す。

```text
Q1 → A, B, C
Q2 → A, D
Q3 → B, E
```

これを利用して、入力文書に対する正解集合を構築する。

```text
入力 A → 正解 B, C, D
入力 B → 正解 A, C, E
```

### 正解集合の定義

文書Aと文書Bが、少なくとも1つの共通するクエリに対して関連ありと判定されている場合、D2D評価上の正解ペアとする。

ただし、これは**文書間の直接的な人手判定ではなく、共通クエリから導出した関連性**である。

実装では、この制約を明示すること。

### qrelsの処理

- 関連性判定が正の文書のみを使用する。
- 未判定文書を「関連なし」と断定しない。
- 入力文書自身を正解集合から除外する。
- 正解候補が存在しない入力文書を評価対象から除外する。
- 複数の正解候補を保持する。
- qrelsの関連性判定値を保存し、将来の段階的評価に備える。

### 評価対象の固定

評価対象文書と正解集合を固定したmanifestを生成する。

同じデータセット・設定から、常に同じ評価対象が生成されるようにする。

ランダムサンプリングが必要な場合は、シードを固定する。

## 4. 評価指標

主指標は **Hit@1** とする。

\[
Hit@1=\frac{\text{正解文書を1位に選択した入力数}}{\text{評価した入力総数}}
\]

例：

| 入力 | 正解集合 | 選択結果 | Hit |
|---|---|---|---|
| A | B, C, D | B | 1 |
| B | A, C, E | F | 0 |
| C | A, B | A | 1 |

この場合：

**Hit@1 = 2 / 3 = 0.667**

### 補助指標

以下も記録する。

| 指標 | 内容 |
|---|---|
| Hit@1 | 1件目の選択精度 |
| Coverage | 評価対象のうち結果を返せた割合 |
| No Result Rate | 候補を発見できなかった割合 |
| Latency | 1ファイルあたりの処理時間 |
| Candidate Count | 発見された候補数 |

検索結果がない場合はHit@1を0とし、分母から除外しない。

## 5. macOS実行環境

**Linuxコンテナだけで評価を完結させてはならない。**

kaseifuはmacOS固有の機能に依存するため、実際の検索・評価はmacOSホスト上で実行する。

### 必要な環境

- macOS
- Rust / Cargo
- Spotlight
- `mdfind`
- `mdls`
- APFSまたはmacOSで利用可能な検証用ファイルシステム

### 実行環境の分離

ベンチマーク専用の作業ディレクトリを用意する。

```text
~/Library/Application Support/kaseifu/benchmark/
├── datasets/
│   └── robust04/
├── corpus/
├── manifests/
├── runs/
└── reports/
```

データセットの展開、検索、評価は、この領域を中心に実行する。

**通常のユーザーファイルを検索対象に含めないこと。**

## 6. Sandbox設計

macOSには複数の隔離方法があるが、今回は次の構成を採用する。

### 推奨：専用macOSユーザー + 専用作業領域

可能であれば、ベンチマーク専用のmacOSユーザーを作成する。

目的は、通常のユーザーファイルと検証環境を分離することである。

ただし、**ユーザーを分離しただけではSpotlightの検索範囲は自動的に制限されない**。

そのため、検索処理側でも対象領域を明示的に制限する。

### Spotlightの検索範囲

`mdfind`を使用する場合、`-onlyin`で検索対象を限定する。

```bash
mdfind -onlyin "$BENCHMARK_CORPUS" "検索条件"
```

検索結果が検証用コーパスの内部に存在することを、パスの正規化後に検証する。

### ファイル操作の禁止

ベンチマーク実行中は、以下を禁止する。

- 実ファイルの移動
- 実ファイルの削除
- ファイル名の変更
- ファイル内容の変更
- 通常のユーザーディレクトリへの書き込み

kaseifuのファイル操作処理は、**dry-runまたは評価専用の読み取りモード**で実行する。

既存のdry-run機能が存在するか確認し、存在しない場合は評価専用の実行経路を実装する。

### macOS Sandboxについて

AppleのApp Sandboxは、通常のCLIに設定を追加するだけで利用できるものではない。

また、`sandbox-exec`は非推奨であり、今回の基盤の必須要件にはしない。

**隔離の中心は、専用作業領域・検索範囲制限・ファイル操作禁止・専用ユーザーとする。**

厳密なOSレベルの隔離が必要な場合は、macOS仮想マシンを追加の選択肢として検討する。

## 7. Spotlightインデックス

macOSのSpotlightは非同期でインデックスを更新する。

そのため、ファイルを配置した直後に評価を開始してはならない。

### 実装要件

1. コーパスを配置する。
2. Spotlightのインデックス状態を確認する。
3. 代表的な文書が`mdfind`で発見できることを検証する。
4. インデックスの準備完了を確認してから評価する。
5. 準備未完了の場合は評価を中止する。

インデックス状態が不完全なまま取得したスコアは、正式な評価結果として扱わない。

また、Spotlightの検索結果には環境依存性があるため、macOSのバージョンとインデックス状態を記録する。

## 8. 評価エンジン

既存のkaseifu実装を再利用する。

ベンチマーク専用の検索アルゴリズムを新規実装してはならない。

### 実行フロー

```text
TREC Corpus
    ↓
Manifest生成
    ↓
入力文書Aを選択
    ↓
kaseifu Discovery
    ↓
候補文書を取得
    ↓
最上位の文書Bを選択
    ↓
Ground Truthと照合
    ↓
Hit@1記録
```

### 重要な実装条件

現在のkaseifuがフォルダ単位の候補選択を行っている場合、**文書候補のランキング結果を評価用に取り出す**。

フォルダランキングの結果をD2Dスコアとして代用してはならない。

また、ベンチマーク用に検索・ランキングのロジックを変更しないこと。

## 9. ベースライン

kaseifuの性能を比較するため、最低限次のベースラインを用意する。

| ベースライン | 内容 |
|---|---|
| Random | 候補文書からランダムに1件選択 |
| BM25 | 文書本文に基づく標準的な語彙検索 |
| kaseifu | 既存のDiscovery処理 |

BM25は既存の標準的な実装を使用する。

ランダムベースラインはシードを固定する。

**これらは今回の派生D2D評価における比較対象であり、TREC公式のQ2Dスコアとは直接比較できない。**

また、kaseifuが本文を使用しない場合、BM25との比較は「同一条件のアルゴリズム比較」ではなく、異なる情報源を利用する手法間の性能比較となる。

## 12. テスト要件

最低限、次のテストを実装する。

1. qrelsの正しい読み込み
2. 多対多関係からの正解集合生成
3. 自己文書の除外
4. Hit@1の正確な計算
5. 検索結果なしの場合の処理
6. 評価対象外パスの拒否
7. ファイル移動・削除が発生しないこと
8. 同一入力から同一manifestが生成されること

10. macOS実環境での統合テスト

以下を満たした時点で完了とする。

- 既存のDiscovery処理を変更せずに評価できる。

- 同じ条件で再実行できる。

## 14. 研究上の重要な制約

この評価基盤には、あらかじめ明記すべき制約が3つあります。

**① TRECのqrelsは網羅的な正解一覧ではない**

未判定文書が実際には関連している可能性があります。そのため、Hit@1の不正解には、未判定の関連文書が含まれる可能性があります。

**② 共通クエリから導出した関連性は、直接的な文書間類似度ではない**

このベンチマークが測るのは、厳密には「共通の情報要求に関連する別文書を選択する能力」です。

**③ 日付・ファイル名などのメタデータによる交絡があり得る**

Robust04のニュース記事には日付などの情報が含まれる場合があります。本文の意味的関連性を測定する研究として解釈する場合は、メタデータの寄与を別途検証する必要があります。

# 15. ファイル散乱アルゴリズム

## 15.1 目的

TREC Robust04の文書コーパスを、macOSの検証用ディレクトリ内に再現可能な方法で分散配置する。

以下の条件を満たすこと。

1. ファイル本文を変更しない。
2. 文書IDと正解データの対応を維持する。
3. 関連文書同士が同じディレクトリに集中しない。
4. ファイル名・配置先・作成日時から正解を推測できない。
5. 同じ設定と乱数シードで同じ配置を再現できる。
6. ベンチマーク終了後に安全に初期状態へ戻せる。

## 15.2 ディレクトリ構造

```text
benchmark/
├── datasets/
│   └── robust04/          # 元データ（変更禁止）
├── workspace/
│   ├── scattered/         # 散乱後のファイル
│   │   ├── dir_0001/
│   │   ├── dir_0002/
│   │   ├── dir_0003/
│   │   └── ...
│   └── manifests/
│       └── scattering.json
└── reports/
```

元データは読み取り専用として扱う。

散乱処理は`workspace/scattered/`以下にファイルを複製して実施する。

## 15.3 散乱アルゴリズム

**推奨方式：Seeded Uniform Random Distribution**

乱数シードを固定した、一様ランダム配置を基本方式とする。

### 処理手順

**Step 1：文書一覧の確定**

TREC文書を文書ID順にソートする。

**Step 2：ファイル名の生成**

文書IDやトピック番号を含まないファイル名を生成する。

例：

```text
7f82a91c.txt
e02d43b7.txt
b71a09c2.txt
```

ファイル名は、文書IDと乱数シードから決定的に生成する。

**Step 3：配置先の決定**

各文書に対して、乱数シードに基づき配置先ディレクトリを決定する。

```text
directory_index = PRNG(seed).next_int(0, directory_count)
```

関連性判定（qrels）は配置処理に使用しない。

**Step 4：ファイルの複製**

決定したディレクトリに本文をコピーする。

**Step 5：manifestの保存**

元の文書IDと実ファイルパスの対応を記録する。

```json
{
  "seed": 42,
  "algorithm": "seeded-uniform-random",
  "files": [
    {
      "doc_id": "DOC001",
      "path": "dir_0003/7f82a91c.txt"
    },
    {
      "doc_id": "DOC002",
      "path": "dir_0001/e02d43b7.txt"
    }
  ]
}
```

## 15.4 日付による交絡の防止

今回の研究では、ファイルの作成日時・更新日時が検索結果に影響する可能性がある。

そのため、以下を実装する。

| 項目 | 要件 |
|---|---|
| ファイル名 | 文書内容・正解ラベルと独立 |
| ディレクトリ名 | 文書内容・正解ラベルと独立 |
| 作成日時 | 配置順序による偏りを抑制 |
| 更新日時 | 全ファイルで同一条件 |
| Spotlightメタデータ | 評価条件として記録 |

### 日付の扱い

macOSの作成日時と更新日時は別の属性である。

**全ファイルに同一の固定日時を設定する方式を基本とする。**

ただし、作成日時は通常のファイルコピー操作だけでは統一できない場合がある。

実装では、macOS上で設定可能な属性を確認し、設定後に`stat`や`mdls`で検証すること。

設定できない属性がある場合は、その事実を記録する。

## 15.5 散乱パターン

最低限、以下の2種類を実装する。

| パターン | 内容 | 目的 |
|---|---|---|
| Flat | 全文書を単一ディレクトリに配置 | ディレクトリ構造の影響を排除 |
| Uniform Random | 複数ディレクトリにランダム配置 | 散乱状態での検索性能を評価 |

**Flatを対照条件、Uniform Randomを散乱条件**として扱う。

両条件で同じ文書集合と正解データを使用する。

## 15.6 複数シードによる検証

散乱配置による偶然の影響を評価するため、複数の乱数シードを使用する。

例：

```text
seed = 42
seed = 123
seed = 2026
seed = 7777
seed = 10001
```

各シードについてHit@1を計算し、平均値と標準偏差を報告する。

ただし、これらは同一文書集合を再配置した反復測定であり、独立したデータセットによる検証ではない。

## 15.7 macOS Sandboxとの統合

散乱処理は、専用ワークスペースの内部でのみ許可する。

**必須の安全対策：**

- 操作対象のパスを正規化する。
- シンボリックリンクによるワークスペース外への脱出を拒否する。
- 散乱処理前に出力先が専用領域内であることを確認する。
- 元データを削除・移動しない。
- 既存ファイルを無条件に上書きしない。
- クリーンアップ対象は、ベンチマーク自身が作成したファイルに限定する。

さらに、**散乱処理とkaseifuの評価処理を分離**すること。

評価実行中は散乱済みファイルを読み取り専用として扱う。

## 15.8 CLI追加

```bash
# 単一ディレクトリ配置
kaseifu-bench scatter --strategy flat

# ランダム散乱
kaseifu-bench scatter \
  --strategy uniform \
  --seed 42 \
  --directories 100

# 散乱状態の検証
kaseifu-bench verify-scatter

# 評価実行
kaseifu-bench run --system kaseifu

# 散乱環境の削除
kaseifu-bench cleanup
```

### 研究上の注意

**今回の散乱は、実際のユーザーのファイル配置を再現するものではありません。**

あくまで、ファイル名・日時・ディレクトリ配置と正解ラベルの関係を制御するための実験条件です。

また、ファイル名をランダム化すると、ファイル名の類似度を利用するkaseifuの性能が低下する可能性があります。

これは不具合ではなく、**本文や検索語から関連ファイルを発見できるかを切り分けるための実験条件**です。

一方、実際のファイル整理性能を測定するには、元のファイル名を保持した別条件が必要です。

**最終的には「元のファイル名 × Flat」「元のファイル名 × Random」「匿名ファイル名 × Flat」「匿名ファイル名 × Random」の4条件を比較すると、ファイル名と配置構造の影響を分離できます。**
