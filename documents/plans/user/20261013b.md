# kaseifu デバッグシナリオ設計書 v1.1

Repository: [https://github.com/smapira/kaseifu](https://github.com/smapira/kaseifu) 対象: Rust / macOS CLI 目的: デバッグシナリオの設計と期待結果の定義 範囲: 設計のみ。実装・テスト実行は行わない。

## 1. デバッグ設計方針

kaseifuの以下のパイプラインを対象とします。

```
File
 ↓
Observe（Filesystem / Spotlight / xattr / EXIF）
 ↓
Normalize
 ↓
Discover
 ↓
Jev Classification
 ↓
Policy（AutoMove / Review / Leave）
 ↓
Execute
 ↓
SQLite Journal
 ↓
Undo
```

Watch、CLI、Config、Auth、Performanceについても横断的に検証シナリオを設計します。

最重要の検証原則は次の4点です。

1. ファイルが消失しないこと。
2. 意図しない上書きが発生しないこと。
3. ファイルとジャーナルの不整合を検出できること。
4. 不正な分類結果によってファイルが移動されないこと。

## 3. 最優先シナリオの具体設計

### S01 — ファイル移動とUndoの一貫性

問い： ファイルの移動と復元によって、元のデータと操作履歴が保たれるか。

- 前提：テスト用の移動元ファイルと既存の移動先ディレクトリを用意する。
- 操作：AutoMove判定 → Execute → Undo。
- 期待結果：元のパスにファイルが復元され、内容が一致する。操作履歴も移動・復元を正しく表す。
- 追加検証：ファイル内容のSHA-256、ファイル数、履歴状態。
- 失敗条件：内容の変化、ファイル消失、二重復元、履歴の矛盾。

### S02 — 未知の移動先IDの拒否

問い： Jevが許可されていない移動先を返しても、ファイルシステムを保護できるか。

- 前提：Discoverが候補ID `D1`、`D2` を返す。
- 入力：Jevが `D999` を選択する。
- 期待結果：未知の候補IDとして拒否し、移動しない。
- 失敗条件：`D999` が採用される、または別の移動先にフォールバックして自動移動する。

### S03 — Policy境界値

問い： AutoMove、Review、Leaveの境界値が仕様どおりか。

| confidence | margin | 期待結果     |
| ---------- | ------ | -------- |
| 0.849      | 0.400  | Review   |
| 0.850      | 0.399  | Review   |
| 0.850      | 0.400  | AutoMove |
| 0.950      | 0.100  | Review   |
| 0.600      | 0.000  | Review   |
| 0.599      | 0.000  | Leave    |

上記は既存READMEに記載されたデフォルト閾値を前提とします。

### S04 — 移動先ファイル衝突

問い： 移動先に同名ファイルが存在しても、双方のデータを保持できるか。

- 前提：移動元と移動先に同名・異内容のファイルを配置する。
- 操作：Execute。
- 期待結果：衝突を検出し、移動を拒否する。
- 検証：両ファイルのパスとハッシュが変化しない。
- 失敗条件：上書き、削除、内容変更。

### S05 — ジャーナル更新中の異常終了

問い： ファイル操作の途中でプロセスが終了しても、データ損失や検出不能な履歴不整合を防げるか。

| 障害発生点         | 確認すべき状態                |
| ------------- | ---------------------- |
| pending記録前    | ファイル未移動、履歴未作成          |
| pending記録直後   | ファイル未移動、未完了履歴が存在       |
| rename直前      | 移動前の状態を識別できる           |
| rename直後      | ファイル移動済み、履歴未確定を識別できる   |
| success更新直前   | 移動済みとpendingの不一致を検出できる |
| success更新直後   | ファイル位置と履歴が整合する         |
| Undoのrename直後 | 復元済みと未確定履歴を識別できる       |
| Undoの履歴更新中    | 二重復元や誤った再実行を防げる        |

現行のジャーナル操作順序から、特に `rename` とDB更新の間が重要な検証点です。

注意： 異常終了後の自動復旧機能が実装済みであるとは確認していません。自動復旧を期待するのではなく、まず状態の検出可能性を検証対象とします。

### S06 — Watchのイベント重複

問い： 同一ファイルに複数のFSEventsが発生しても、重複処理や誤移動を防げるか。

- 500ms以内に複数イベントを発生させる。
- ファイルの書き込み中にイベントを発生させる。
- 処理中に同じファイルを再通知する。
- 移動後に自己生成イベントを発生させる。
- 監視中にファイルを削除する。

期待結果は、重複排除、安定性確認、自己イベント抑制、処理失敗の分離です。

### S07 — メタデータ欠損・競合

問い： SpotlightとEXIFの情報が不足・矛盾しても、存在しない情報を生成せずに処理できるか。

検証条件：

- Spotlight未索引
- EXIFなし
- 撮影日時なし
- GPS緯度のみ
- SpotlightとEXIFで異なる撮影日時
- 破損したJPEG
- HEICのメタデータ取得失敗

期待結果は、取得できた証拠の出典が保持され、欠損値が推測で補完されないことです。

### S08 — Jev通信・応答障害

問い： 外部分類サービスの障害がファイル操作に波及しないか。

検証条件：

- HTTP 401 / 403
- HTTP 500 / 503
- タイムアウト
- 接続拒否
- 空レスポンス
- 不正JSON
- NaN / Infinity
- 未知の候補ID

期待結果は、適切なエラー処理が行われ、ファイルが移動されないことです。

## 4. 追加設計シナリオ

| ID  | 検証条件                 | 期待結果                |
| --- | -------------------- | ------------------- |
| S09 | Dry-runを実行           | ファイルと履歴に移動完了の副作用がない |

## 5. シナリオの評価基準

各シナリオは次の項目で管理します。

```
scenario_id: S01
title: "Move and Undo consistency"
priority: P0
test_level: E2E

question: "移動と復元でデータと履歴の整合性が保たれるか"

preconditions:
  - "テスト用ファイルが存在する"
  - "移動先ディレクトリが存在する"

inputs:
  - "AutoMove判定"
  - "Execute"
  - "Undo"

expected:
  - "ファイルが元のパスに復元される"
  - "ファイル内容のハッシュが一致する"
  - "操作履歴が整合する"

failure_conditions:
  - "ファイル消失"
  - "内容変更"
  - "二重復元"
  - "履歴不整合"

existing_test: "tests/phase5_execute_test.rs"
status: DESIGNED
```

`status: DESIGNED` は設計済みを意味し、テスト成功を意味しません。
