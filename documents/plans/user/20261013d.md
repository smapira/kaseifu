# kaseifu ゼロコンフィグ化 改善計画 v1.0

**Repository:** https://github.com/smapira/kaseifu
**基準:** v0.5.0（`5511c72`）／`documents/plans/user/20261013b.md`（デバッグシナリオ設計書 v1.1）
**目的:** インストール直後のユーザーが、設定書類や環境変数を理解しなくても kaseifu を使い始められるようにする（ゼロコンフィグ）
**範囲:** 初回体験・実行時UX・安全性の可視化。判定ロジック（Jev/Policy）の意味は変えない

---

## 1. 背景（実測済みの問題）

実機セッションと計測から、次の4点が「インストールしてもすぐ使えない」直接原因になっている。

| # | 問題 | 実測エビデンス |
|---|---|---|
| A | 実行ディレクトリごとに `data/` が作られる（ジャーナルが CWD 相対） | `~/Desktop/images/data/kaseifu.db` と `~/Desktop/test/data/kaseifu.db` が実際に存在（各 12KB・0行）。ユーザーのフォルダを汚す |
| B | 同じファイルで判定が反転する | `classify IMG_2741.jpeg` → confidence 0.85・AUTO MOVE、13秒後の `organize` → 0.840・**REVIEW**。閾値直上での揺れ |
| C | APIキー未設定だと Jev 系コマンドが即エラー | `classify` / `organize` は「no API key is configured」で終了。`setup` を知らないと行き止まり |
| D | 素の `kaseifu` が案内を出さない | 引数なしは usage エラー（exit 2）。初回ユーザーに次に何をすべきか伝わらない |
| E | **人間が移動先を選べない** | `classify vape_ad_20260913_v2_final.MP4` → Jev の順位は D1 56% / NONE 24% / D2 20%、policy は LEAVE。「3番目の D2 へ置きたい」と思っても指定する手段が無い（`organize` の引数は `--execute` / `--dry-run` のみ） |

補足: `policy` は独立コマンドではなく、Jev の選択を Rust 側が実行可否に翻訳した結果（`AUTO MOVE` / `REVIEW` / `LEAVE`）である。この概念がコマンドに見えるため `kaseifu policy -h` のような誤入力が起きやすい。

---

## 2. 目標

**「インストール → 1コマンド」で価値が伝わり、追加設定なしで安全に使えること。**

- 鍵・閾値・ジャーナル・補完の配置は**既定で妥当**であり、ユーザーが調べなくてよい
- 何か足りない場合、**次に打つべき1コマンド**がその場で提示される
- 破壊的操作は従来どおり `--execute` が必須で、既定はドライラン

## 3. 対象範囲

- 対象: 初回体験（引数なし実行・鍵未設定時）、`doctor` の診断内容、ジャーナル既定位置、判定の説明可能性、JSON出力の穴、アンインストール、ドキュメント
- 対象外: Jev の判定ロジック・閾値の意味（既定値の変更を含む）、Discovery の候補生成規則、動画対応の実装可否の決定（本計画では「明示する」まで）

## 4. P0 要件（ゼロコンフィグの核）

### ZC-1. 鍵が無いときでも使い始められる

- Jev 依存コマンド（`classify` / `organize` / `watch`）で鍵が未解決のとき:
  - **TTY の場合**: その場で APIキーのマスク入力を促し、未設定なら以降の処理に進まない。保存先は取得モードに従う（リリース既定 `auto` は Keychain、`env` モードは `.env`）
  - **非TTY の場合**: 従来どおり明確なエラーで終了（終了コード非0）し、**鍵なしで使えるコマンドを案内**する（`inspect`, `doctor` は Jev を呼ばない）
  - 入力値はログ・画面・エラー文に残さない。中断時は何も保存しない
- 受け入れ基準:
  1. 鍵未設定の TTY 実行で、対話入力→保存→処理続行の経路が動作する（実測）
  2. 非TTY 実行ではハングせず、案内文つきで非0終了する
  3. 入力された鍵が出力・ログ・JSON に現れない（grep で0件）
  4. `env` モードでは Keychain に触れない（既存の非接触保証を維持）

### ZC-2. 素の `kaseifu` を案内表示にする

- 引数なし実行で、次を表示して終了する（usage エラーにしない）:
  - 概要1行、`classify` / `organize` / `doctor` の3コマンドと用途
  - 「`--execute` を付けない限りファイルは動きません」の明示
  - 鍵未設定なら `setup`（または ZC-1 の対話）を案内
- 受け入れ基準:
  1. 引数なしで終了コード 0、上記内容が表示される
  2. `--help` は従来どおり全コマンドを表示する（互換維持）
  3. ネットワーク・ファイルシステムへの副作用がない（`data/` を作らない）

### ZC-3. ジャーナルをユーザー領域へ（CWD 相対の解消）

- 既定をユーザー単位の安定した絶対パス（`~/Library/Application Support/kaseifu/`）にする
- 旧 `./data/kaseifu.db` は**移動・削除・上書きしない**。`doctor` が「カレントディレクトリに旧ジャーナルがある」と検出して報告し、0行なら安全に削除してよい旨を表示する
- 受け入れ基準:
  1. 任意のディレクトリで実行しても `data/` が作られない（実測）
  2. `doctor` が解決後のジャーナルパスと旧ジャーナルの有無を表示する
  3. 既存の空 `data/` を残しても動作に影響しない
- 注記: 本要件は進行中の改修（R5相当）と同一。重複実装しない

### ZC-4. `doctor` を「今すぐ使えるか」の1枚にする

- 既存の診断項目（Platform / Configuration / API Key / Jev Endpoint / Spotlight / Storage / Completion）に**ジャーナル検査**を加える
- **FAIL 行には次に打つ1コマンドを必ず併記**する（例: `kaseifu setup`、`kaseifu completions zsh --install`）
- ネットワークは `--check-connection` 指定時のみ。副作用はディレクトリ作成に留める
- 受け入れ基準:
  1. 各 FAIL 行に実行可能なコマンドが併記される（実測の表示例で確認）
  2. 正常環境では全項目 ok で終了コード 0
  3. 鍵未設定でも `env` モードで即時完了（ハングなし）

## 5. P1 要件（体感の質）

### ZC-5. 閾値近傍の可視化

- `classify` / `organize` の表示で、AUTO MOVE 直下（例: confidence 0.80〜0.85）のとき「あと◯で自動移動」等の近接表示を出す
- `--explain` を追加し、判定根拠（confidence / margin / 適用閾値 / 選択候補の解決先）を1画面で示す
- 自動ヒステリシス（判定の時間的平滑化）は**導入しない**（説明可能性を優先）
- 受け入れ基準: 近接表示と `--explain` の出力をテストで固定。既存の表示・JSONは不変

### ZC-6. `policy` の概念を明示する

- `--help`（トップレベル）または `doctor` に、`AUTO MOVE` / `REVIEW` / `LEAVE` の閾値と意味、**実行には `--execute` が必要**であることを明記する
- 独立コマンドは追加しない（概念の説明に留める）
- 受け入れ基準: ヘルプまたは doctor から閾値と3値の意味が読み取れること

### ZC-7. `organize --format json`

- `organize` の結果（decision / policy / outcome）を構造化して出力する。既存の `inspect` / `classify` / `discover` のJSON流儀に合わせる
- 既存キーを削除しない（追加のみ）
- 受け入れ基準: JSON をパースして decision / policy / outcome が取得できる。プレーン表示は不変

### ZC-8. 動画の扱いを明示する

- MP4 / MOV は現状、画像判定の対象外（`is_image_file` は画像8拡張子のみ）で、撮影日時・GPS は Jev に渡らない
- 本計画では**対応可否を決定しない**。README と `doctor`（または `--help`）に「現状の対象」と「対象外」を明記し、期待値のずれを防ぐ
- 受け入れ基準: ドキュメントに対象/対象外が明記される

## 7. アンインストール要件（ZC-11）

**方針: kaseifu が作ったものだけを対象にし、ユーザーのデータとファイルは既定で残す。**

### ZC-11. `kaseifu uninstall`

- **既定はドライラン**。何も削除せず、対象の一覧と合計サイズを表示して終了 0。実行には `--execute` を要する（他コマンドと同じ安全原則）
- 対象の分類と既定の扱い:

| 対象 | 既定 | 備考 |
|---|---|---|
| 補完スクリプト（検出ディレクトリの `_kaseifu`） | 削除 | 再生成可能。失敗しても続行 |
| ユーザ設定 `~/Library/Application Support/kaseifu/config.toml` | **保持** | `--purge` 指定時のみ削除 |
| ジャーナル `kaseifu.db`（同ディレクトリ） | **保持** | 削除すると `undo` 履歴が失われる。`--purge` 時に**影响を明示**して削除 |
| Keychain のAPIキー（`com.routeflags.kaseifu.jev`） | **保持** | `--remove-key`（または `--purge`）で削除。対話確認あり、`--yes` で省略可 |
| 旧 `./data/kaseifu.db`（カレントディレクトリ） | 保持・列挙のみ | 削除はカレントディレクトリのものに限り、`--execute --purge` のときのみ。**他ディレクトリの旧ジャーナルは削除せず列挙・案内のみ** |
| バイナリ `~/.cargo/bin/kaseifu` | 削除しない | cargo 管理。`cargo uninstall kaseifu` を案内する |

- **kaseifu が移動したユーザーファイル・ディレクトリには一切触れない**（アンインストールの対象外であることを表示）
- 実行順序: 補完 →（指定時のみ）設定・ジャーナル → 最後に Keychain。途中で失敗しても他を巻き戻さない（部分削除の事実を表示）
- 補完の自動更新との関係: バイナリが残っていると次回の実行で補完が再生成される。その旨を表示して `cargo uninstall kaseifu` を案内する
- `KASEIFU_KEY_SOURCE=env` では Keychain に**触れない**（読みも削除も）
- 表示: ASCII のみ。`doctor` と同系のチェック行で対象/保持を区別する。`--format json` で対象一覧を構造化出力する（ZC-7 と同じ流儀）
- 受け入れ基準:
  1. 既定（ドライラン）で何も削除されず、対象とサイズが表示される（実測）
  2. `--execute` で補完のみ削除され、設定・ジャーナル・Keychain は残る（実測）
  3. `--purge --execute` で設定・ジャーナルを削除し、`--remove-key --yes` で Keychain から削除できる
  4. `env` モードでは Keychain に触れない（テストで証明）
  5. 2回実行しても安全（冪等・「削除対象なし」で終了 0）
  6. 移動済みファイルと他ディレクトリの旧ジャーナルを削除しない
  7. テストは一時ディレクトリと注入経路のみを使い、実ユーザーの設定・ジャーナル・Keychain を読み書きしない

## 8. ヘルプ表示の見直し（ZC-12）

実測（v0.5.0 の全ヘルプ 389 行を探索）で、**ユーザーの操作に関係しない記載**と**実装と食い違う記載**が見つかっている。

### ZC-12. ヘルプを「ユーザーの操作に必要な情報」だけにする

**除去・置換するもの（実測で確認済みの出現箇所）**

| 種別 | 例（現状の文言） | 扱い |
|---|---|---|
| 内部フェーズ番号 | `classify` = "Run the full decision pipeline for one file (Phase 4)"、`watch` = "... (Phase 6)" | 削除する（ユーザーにとって意味がない） |
| パイプライン語 | `organize` = "decision -> policy -> plan -> (dry-run or move)"、`classify` long help = "Observe -> Normalize -> Discover -> Jev -> validated JevDecision. ... (execution is a later phase)" | ユーザー行動の言葉（「整理先を判断し、確認した上で移動します」等）に置換 |
| 内部型名 | `inspect` = "Build and display FileContext JSON"、`--verbose` = "Show the DETAILS layer (full paths, schema, raw metadata)" | 「ファイルの観察結果（JSON）を表示」等に置換。内部型名は残さない |
| 実装と不一致の機能説明 | `scan` = "Scan a directory"（実際はバナー出力のみ） | 実態に合わせるか、コマンド自体を非表示化/廃止する判断を記録 |
| 未対応フラグの提示 | `--format json` が `organize`/`undo`/`scan`/`watch` で動かないのに `[possible values: auto, rich, json]` と表示（F-07） | 対応するまではその旨を明記するか、フラグを提示しない（ZC-7 と整合させる） |
| 対応範囲の不明確さ | `completions <SHELL>` は 6 シェルを列挙するが `--install` は zsh のみ | どちらで何ができるかを1行で明確に |
| フラグの重複・混乱 | `--execute` "Actually perform the move (default is a dry run)" と `--dry-run` "Explicitly request a dry run (the default)" が並び、相互排他（clap `conflicts_with`）であることが読み取れない | 排他関係と既定を1行で明示（例: "既定はドライラン。`--execute` と `--dry-run` は同時に使えない"） |
| `-h` と `--help` の差 | "Print help (see more with '--help')" / "see a summary with '-h'" の相互参照 | 両方で同じ用語を使い、内部情報の差だけにする（詳細に段階名を入れない） |

**維持するもの（消してはいけない）**

- 安全性の明示: 既定はドライラン、「`--execute` を付けない限りファイルは動かない」
- 鍵の経路: Keychain / `KASEIFU_KEY_SOURCE` / `.env` の関係（ZC-1・ZC-6 と整合）
- 各コマンドの用途と代表的な使用例（1行）
- ネストしたサブコマンド（`auth` / `config`）の一覧

**受け入れ基準**

1. 全ヘルプ出力（トップレベルと全サブコマンド、`-h` と `--help` の両方）に以下が現れない: `Phase`、内部型名（`FileContext`、`JevDecision` 等）、パイプライン語（`Observe -> Normalize -> ...`、`decision -> policy -> plan`）。テストで固定する
2. ヘルプに表示されるフラグは、そのコマンドで実際に機能するものだけである（未対応なら表示しないか、未対応と明記する）
3. 安全性（ドライラン既定・`--execute` 必須）と鍵経路の情報は、ヘルプから読み取れる
4. README と `doctor` の語彙と矛盾しない
5. ASCII のみ・幅整合を維持し、既存のヘルプテストがあれば更新する

## 9. 対話的な移動先選択（ZC-13）

背景 E の解決。Jev の選択は**提案**であり、最終決定を人間が行える経路を用意する。

### ZC-13. 候補から対話的に移動先を選ぶ

**コマンド形**（実装時にどちらかに確定し、計画書に理由を記録する）

- 推奨: `kaseifu organize <file> --select` — 既存コマンドの対話モード。現在の `organize <file>` を壊さない
- 代替: トップレベル `kaseifu select <file>` — サブコマンドとして見せたい場合。内部で同じ対話フローを呼び、`--select` と同じ振る舞いにする（**真の入れ子サブコマンド** `organize select <file>` は、既存の位置引数 `FILE` と共存できず既存利用を壊すため採用しない）

**振る舞い**

1. 候補を Discovery で列挙し、番号付きで表示する（パス、スコア、既存ファイル数などの根拠）。**Jev は呼ばない**（鍵不要で動作する。ゼロコンフィグの一部）
2. 鍵がある場合でも、Jev の選択は**参考表示のみ**（例: 「Jevの提案: D1」）。実行の決定権はユーザーにある
3. 選択は番号入力。`q` または Ctrl+C で**何も変更せず終了**（終了コード 0）
4. 選択後は「移動計画」（from → to）を表示し、既定はドライラン。`--execute` で実行し、実行前に確認を求める（`--yes` で省略）
5. **非TTY では対話を開始しない**。明確なエラーを返し、代替手段（`--format json` で候補列挙、将来の ZC-14 `--to <dir>`）を案内する
6. `--format json` では対話を行わず、候補一覧（ID・パス・スコア）を構造化出力する

**安全要件（既存の原則を継承）**

- 移動先の妥当性を検証: 存在するディレクトリであること。`~/Library/**`・`*.library/**`・キャッシュ・機械生成名など**移動先になれない場所は拒否**（v0.4.2 の除外規則を再利用）
- 自身の親ディレクトリは選択肢に出さない（no-op の防止）
- 同名ファイルの衝突は上書きせず拒否（既存規則を維持）
- 移動は**ジャーナルに記録し `undo` で戻せる**。人間が選んだ移動は Jev の confidence/margin を持たないため、journal 上で区別できるようにする（例: `manual` フラグ／`candidate_id=NULL`）。`undo` / `doctor` の表示を矛盾なくする
- 表示で「人間が指定した移動」であることを明示する（例: `[MANUAL]`）
- 鍵が未設定でも動作する（Jev を呼ばないため。`doctor` の診断は不要）

**受け入れ基準**

1. TTY で候補一覧が表示され、番号選択→移動計画→（`--execute` 時のみ）移動が行われる（実測）
2. `q` / Ctrl+C でファイル・ジャーナルに一切の変更が残らない
3. 非TTY では対話を開始せず、非0で終了する
4. 除外規則に該当する候補（`~/Library` 等）は選択肢に出ない。選んでも拒否される
5. 選択した移動が `kaseifu undo` で戻り、`doctor` / journal の表示と矛盾しない
6. 鍵未設定（`KASEIFU_KEY_SOURCE=env` かつ未設定）でも対話選択が動作し、Jev へのリクエストが発生しない
7. テストは注入した入力（疑似TTY/標準入力）と一時ディレクトリのみを使い、実ユーザーのファイル・ジャーナル・Keychain を読み書きしない

## 10. 非機能要件

- 秘密情報: APIキーを引数・ログ・JSON・コミットに含めない。`.env` とKeychainの取得モード分離（`KASEIFU_KEY_SOURCE`）を維持する
- 安全: 既定はドライラン。移動は `--execute` 必須。ジャーナルと Undo の意味を変えない。既存ユーザーデータの移動・削除は行わない
- 表示: ASCII のみ。`NO_COLOR` / 非TTY に従う。TUI は導入しない
- 互換: 既存JSONのキーを削除しない。`discover` はデバッグ専用（`--help` 非表示）を維持
- 品質: `bash scripts/quality_check.sh` が OVERALL PASS。新規 CC16+ を作らない。新規依存は原則追加しない
- テスト: 各要件に振る舞いテストを追加。実ユーザーのディレクトリ（`~/Desktop`、`~/Library/Application Support/kaseifu`）や実Keychainをテストで読み書きしない

## 11. 実装順序と依存

1. **先行（進行中）**: ジャーナル絶対パス化（ZC-3）・除外規則の是正・設定の正直化
2. **P0**: ZC-1 → ZC-2 → ZC-4（ZC-3 は先行分の完了を前提に検証のみ）
3. **P1**: ZC-5 → ZC-6 → ZC-7 → ZC-8 → ZC-12 → ZC-13
4. **仕上げ**: ZC-11（アンインストール）→ ZC-9 → ZC-10
