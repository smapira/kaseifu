# kaseifu 開発追加指示書 v3.2
## Image Metadata & Context-Aware Classification

**対象リポジトリ：** https://github.com/smapira/kaseifu  
**対象環境：** Rust / macOS  
**適用先：** 開発指示書 v3.0 / v3.1  
**目的：** 画像の撮影日時・位置情報・カメラ情報を取得し、Jevによるファイル整理判断の精度を改善する。

---

## 1. 基本方針

kaseifuの既存アーキテクチャを維持し、画像ファイルの観測能力を拡張する。

```text
Image File
    │
    ▼
Rust Observe
    ├─ Spotlight Metadata
    ├─ EXIF Fallback
    └─ Metadata Normalization
    │
    ▼
Rust Discovery
    ├─ Spotlight Search
    ├─ Candidate Directories
    └─ Evidence Files
    │
    ▼
Jev Classification
    ├─ Filename
    ├─ Semantic Signals
    ├─ Capture Date
    ├─ GPS Location
    ├─ Camera Information
    └─ Directory Context
    │
    ▼
Rust Policy
    ├─ AutoMove
    ├─ Review
    └─ Leave
```

**Rustはメタデータを取得・正規化する。Jevはその意味を評価する。**

撮影日時やGPSに独自のランキング点数を付けない。

---

## 2. 取得対象のメタデータ

### P0 — 必須

| 項目 | Spotlight属性 | 用途 |
|---|---|---|
| 撮影日時 | `kMDItemEXIFDateTimeOriginal` | 撮影時期の特定 |
| コンテンツ作成日時 | `kMDItemContentCreationDate` | 撮影日時の補助 |
| 緯度 | `kMDItemLatitude` | 撮影場所の特定 |
| 経度 | `kMDItemLongitude` | 撮影場所の特定 |
| 高度 | `kMDItemAltitude` | 位置情報の補助 |
| カメラメーカー | `kMDItemAcquisitionMake` | 撮影機器の識別 |
| カメラ機種 | `kMDItemAcquisitionModel` | 撮影機器の識別 |
| 画像幅 | `kMDItemPixelWidth` | 画像属性 |
| 画像高さ | `kMDItemPixelHeight` | 画像属性 |

### P1 — 追加候補

| 項目 | Spotlight属性 |
|---|---|
| ISO感度 | `kMDItemISOSpeed` |
| 露出時間 | `kMDItemExposureTimeSeconds` |
| F値 | `kMDItemFNumber` |
| 焦点距離 | `kMDItemFocalLength` |

各属性の存在・取得可否をmacOS上で確認すること。

Spotlight属性は、ファイル形式やインデックス状態によって取得できない場合がある。

属性が存在しない場合、値を推測して埋めてはならない。

## 3. Spotlightを第一取得手段とする

macOS標準の `mdls` / Metadata APIを使用する。

PoCコマンド：

```bash
mdls \
  -name kMDItemEXIFDateTimeOriginal \
  -name kMDItemContentCreationDate \
  -name kMDItemLatitude \
  -name kMDItemLongitude \
  -name kMDItemAltitude \
  -name kMDItemAcquisitionMake \
  -name kMDItemAcquisitionModel \
  -name kMDItemPixelWidth \
  -name kMDItemPixelHeight \
  image.jpg
```

### 実装要件

- 既存の `platform/macos/spotlight` 実装を調査する。
- 可能なら既存のメタデータ取得処理を拡張する。
- 同じファイルに対する不要なSpotlight呼び出しを避ける。
- 属性名・値・取得元を保持する。
- `null`、未取得、取得失敗を区別する。
- Spotlight取得失敗時も分類処理を継続できるようにする。

**取得できないメタデータは、取得できないまま扱う。**

## 4. EXIF直接解析をFallbackとして追加

Spotlightで必要な属性が得られない場合に限り、画像ファイル内のEXIFを直接解析する。

対象形式：

- JPEG
- HEIC / HEIF
- TIFF

PNG、WebPなどは対応可能なメタデータ形式を個別に確認する。

### Rust実装

まず既存依存関係を調査する。

EXIF解析ライブラリの候補として `kamadak-exif` などを評価する。

ただし、ライブラリ名だけで全画像形式に対応していると判断しないこと。

HEIC / HEIFについては、macOSのImageIOを利用する方法も比較する。

### 優先順位

```text
Spotlight
    ↓ 値がない場合
EXIF / ImageIO
    ↓
Normalized Metadata
```

両方で値が取得できた場合は、取得元を記録する。

値が矛盾する場合、無条件に一方で上書きしない。

---

## 5. 日時の正規化

以下の日時を区別する。

| 種別 | 意味 |
|---|---|
| Capture Date | 実際の撮影日時 |
| Content Creation Date | コンテンツの作成日時 |
| File Creation Date | ファイルシステム上の作成日時 |
| File Modification Date | ファイル更新日時 |

**ファイル更新日時を撮影日時として扱わないこと。**

EXIF日時にタイムゾーンがない場合、勝手にUTCや端末のタイムゾーンを割り当てない。

概念モデル：

```json
{
  "capture_time": {
    "value": "2025-08-10T15:30:00",
    "timezone": null,
    "source": "exif",
    "timezone_known": false
  }
}
```

日時の由来を保持し、Jevにも区別できるようにする。

---

## 6. GPS情報の正規化

対象：

- Latitude
- Longitude
- Altitude

GPS座標は数値として保持する。

```json
{
  "location": {
    "latitude": 35.658,
    "longitude": 139.702,
    "altitude_m": null,
    "source": "spotlight"
  }
}
```

このJSONはデータ構造の例であり、実際の撮影場所ではない。

### 検証

- 緯度は -90〜90
- 経度は -180〜180
- NaN / Infinityを拒否
- 不完全な座標を識別
- 取得元を記録
- GPSが存在しない画像を正常に処理

逆ジオコーディングによる地名変換は、このフェーズでは必須としない。

---

## 7. NormalizedFileContextの拡張

画像専用のメタデータ構造を追加する。

概念モデル：

```json
{
  "image_metadata": {
    "capture_time": {
      "value": "2025-08-10T15:30:00",
      "timezone_known": false,
      "source": "exif"
    },
    "location": {
      "latitude": 35.658,
      "longitude": 139.702,
      "source": "spotlight"
    },
    "camera": {
      "make": "Apple",
      "model": "iPhone"
    },
    "dimensions": {
      "width": 4032,
      "height": 3024
    }
  }
}
```

既存の `NormalizedFileContext`、`DecisionContext`、シリアライズ処理を確認する。

画像以外のファイルでは `image_metadata` を省略可能とする。

既存JSONの互換性を考慮する。

## 8. Jevへの情報伝達

**取得したメタデータを、Jevが実際に参照できるリクエストへ追加すること。**

`inspect` に表示するだけでは不十分である。

現在のJevリクエスト生成処理を調査し、画像メタデータを追加する。

概念例：

```json
{
  "target": {
    "filename": "IMG_1234.HEIC",
    "type": "image/heic",
    "image_metadata": {
      "capture_time": "2025-08-10T15:30:00",
      "location": {
        "latitude": 35.658,
        "longitude": 139.702
      },
      "camera_model": "iPhone"
    }
  }
}
```

これは概念例であり、Jev APIの正式なリクエストスキーマではない。

**実際のJev API仕様を確認し、対応するフィールドへマッピングすること。**

未対応フィールドを勝手に追加しない。

### Jevの判断方針

Jevには以下を考慮させる。

- ファイル名
- 撮影日時
- 撮影場所
- カメラ情報
- 候補ディレクトリ
- 既存ファイルとの関連性

例：

```text
Target:
  IMG_1234.HEIC
  Captured: 2025-08-10
  Location: GPS available

Candidates:
  D1: Photos/2025/Summer
  D2: Photos/Travel
  D3: Documents/Receipts
```

Jevが候補の文脈を評価する。

撮影日時やGPSに対してRust側で独自の適合度スコアを計算しない。

# Part B — 気象情報

## 10. 気象情報はPhase 2として扱う

Spotlightの画像メタデータには、通常、撮影時の天候が含まれない。

したがって、気象情報は外部データから取得する。

```text
Capture Date + GPS
       ↓
Historical Weather API
       ↓
Weather Context
       ↓
Jev Classification
```

### 取得候補

- 気温
- 降水量
- 天候コード
- 風速
- 湿度

候補サービス：

- Open-Meteo Historical Weather API
- 気象庁の過去気象データ

APIの対応期間、地域、利用規約、データ精度を確認する。

### 実装条件

- 撮影日時が取得できること
- 位置情報が取得できること
- タイムゾーンが適切に解決できること
- 外部API利用が許可されていること

位置情報がない場合は、気象情報を推測しない。

### 非機能要件

- 気象APIはオプション
- 既定では外部通信しない
- キャッシュを設ける
- タイムアウトを設定する
- API失敗時も分類を継続する
- 観測値と推定値を区別する

気象情報は写真から直接読み取った事実ではなく、外部データとの照合結果であることを保持する。

# Part C — プライバシーと安全性

## 11. 位置情報の取り扱い

GPSは個人の行動履歴につながる情報である。

外部のJev APIに送信する場合、明示的な設定で制御できるようにする。

設定例：

```toml
[metadata.image]
enabled = true
spotlight = true
exif_fallback = true

[metadata.privacy]
send_capture_time_to_jev = true
send_gps_to_jev = false

[metadata.weather]
enabled = false
```

上記は提案する設定形式であり、既存の設定スキーマではない。

### 必須事項

- GPSの外部送信は既定で無効
- APIキーをログに出力しない
- 位置情報を不要に永続保存しない
- ログで位置情報をマスクできる
- GPS送信を無効化しても分類が動作する

## 13. 実装順序

### Phase 1 — Spotlight PoC

実際のmacOS画像で `mdls` を実行する。

取得できる属性と取得できない属性を記録する。

### Phase 2 — Metadata Extraction

Spotlightの画像属性取得を実装する。

### Phase 3 — EXIF Fallback

Spotlightで不足する情報をEXIF / ImageIOで補完する。

### Phase 4 — Normalization

日時・GPS・カメラ情報を型付き構造に正規化する。

### Phase 5 — Jev Integration

Jevリクエストに画像メタデータを追加する。

実際の送信内容をテストで検証する。

### Phase 6 — Rich CLI

`inspect` の画像メタデータ表示を実装する。

### Phase 7 — Validation

```bash
cargo fmt --check
cargo check
cargo test
```

macOSで実ファイルを使用した検証を実施する。

### Phase 8 — Weather Extension

P0の動作確認後、別タスクとして気象情報を実装する。

## 最終原則

**Spotlightを優先し、EXIFで補完する。Rustは撮影情報を正確に取得し、Jevはその情報を利用して整理先を判断する。**

気象情報は外部データとして後から追加する。

メタデータの取得元を保持し、判断の根拠を追跡可能にする。
