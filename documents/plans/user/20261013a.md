# kaseifu 開発指示書 v3.4
## Rust Static Analysis & Complexity Management

**Repository:** https://github.com/smapira/kaseifu  
**Language:** Rust  
**Priority:** P1  
**Scope:** Lint / Formatting / Cyclomatic Complexity / CI  
**目的:** 静的解析とコード複雑度の継続的な品質管理

---

## 1. 開発目的

kaseifuに、コード品質を定量的に測定・管理する仕組みを導入する。

管理対象は以下の4項目とする。

| 分類 | 指標 | ツール |
|---|---|---|
| Formatting | フォーマット違反 | rustfmt |
| Lint | 警告・問題検出 | Clippy |
| Cyclomatic Complexity | 循環的複雑度 | rust-code-analysis |
| Testing | テスト結果 | cargo test |

循環的複雑度（Cyclomatic Complexity、以下CC）は、制御フローにおける独立した経路の複雑さを表す指標である。

Clippyの認知的複雑度（Cognitive Complexity）とは区別して管理する。

---

## 2. 基本設計方針

### 必須要件

1. Rust公式ツールを優先する。
2. 循環的複雑度は関数単位で管理する。
3. JSON形式のレポートを保存する。
4. ローカルとCIで同一の検査を実行できる。
5. 既存コードを一括リファクタリングしない。
6. 品質基準を超えた箇所を一覧化する。
7. 既存のテスト・ビルド・実行動作を維持する。

### 品質管理フロー

```text
Rust Source
    │
    ├── rustfmt
    │      └── Formatting Check
    │
    ├── Clippy
    │      └── Lint Diagnostics
    │
    ├── rust-code-analysis
    │      └── Cyclomatic Complexity
    │
    └── cargo test
           └── Test Results
    │
    ▼
Quality Reports
    │
    ├── Lint Summary
    ├── Complexity Ranking
    ├── Threshold Violations
    └── CI Result
```

# Part A — Rust Lint

## 3. rustfmtの導入

Rust標準のフォーマッターを使用する。

### インストール確認

```bash
rustup component add rustfmt
```

### 実行

```bash
cargo fmt --all -- --check
```

### 要件

- 既存のRustコード全体を検査する。
- フォーマット違反を検出する。
- CIでは自動修正しない。
- ローカルでは `cargo fmt --all` により修正可能とする。

---

## 4. Clippyの導入

Clippyを標準Lintとして採用する。

### インストール確認

```bash
rustup component add clippy
```

### 実行

```bash
cargo clippy --all-targets --all-features -- -D warnings
```

### 管理対象

- 不必要なClone
- 非効率なイテレーション
- 不適切なエラー処理
- 冗長な条件分岐
- 型の扱い
- 潜在的なバグ
- 複雑なコード構造

### 運用基準

新規コードはClippy警告0件を目標とする。

既存コードに警告が存在する場合、まず現状を計測し、修正範囲を決定する。

Lint抑制を追加する場合は、理由を明記する。

```rust
#[allow(clippy::too_many_arguments)]
// 理由を明示すること
```

原則として、警告を隠すためだけの広範囲な `allow` を禁止する。

# Part B — 循環的複雑度

## 5. rust-code-analysisの導入

Mozillaの `rust-code-analysis` を採用候補とする。

Repository:

https://github.com/mozilla/rust-code-analysis

CLI:

```bash
cargo install rust-code-analysis-cli
```

### 導入前の検証

開発者は次の事項を確認すること。

- 現在のRust toolchainでビルド可能か
- 対象リポジトリの最新リリース
- Rust構文への対応状況
- CCメトリクスの定義
- 関数単位の測定可否
- JSON出力仕様
- ライセンス
- CI環境での動作

**実際のCLIオプションとJSON構造を確認してから、集計スクリプトを実装すること。**

インストールや動作に問題がある場合、代替ツールを調査して報告する。動作確認なしにツールを固定しない。

---

## 6. 複雑度測定

想定コマンド：

```bash
rust-code-analysis-cli -m -p src
```

JSON出力：

```bash
rust-code-analysis-cli -m -p src -O json -o reports/complexity
```

上記は導入候補のコマンドであり、採用するバージョンでオプションを検証すること。

### 測定対象

- 通常の関数
- impl内のメソッド
- 非同期関数
- ネストした制御フロー
- match式
- if / else
- loop / while / for

マクロ展開や生成コードについては、解析器の対応範囲を確認する。

### 必須データ

関数単位で次の情報を記録する。

```json
{
  "file": "src/classifier/pipeline.rs",
  "function": "classify_report",
  "start_line": 42,
  "end_line": 120,
  "cyclomatic_complexity": 8
}
```

このJSONはkaseifu側の正規化レポート形式の提案であり、rust-code-analysisのネイティブ出力形式ではない。

---

## 7. 複雑度の品質基準

初期基準は以下とする。

| CC | 判定 | 対応 |
|---|---|---|
| 1〜10 | Normal | 許容 |
| 11〜15 | Review | レビュー対象 |
| 16以上 | Refactor | 改善候補 |

これらはプロジェクト独自の運用基準であり、Rust公式の閾値ではない。

### 重要事項

初回導入時に、既存の高複雑度関数を理由としてCI全体を失敗させない。

まずベースラインを作成する。

その後、新規・変更コードの複雑度悪化を検出する。

# Part C — レポート基盤

## 8. ディレクトリ構成

推奨：

```text
scripts/
├── quality_check.sh
└── complexity_report.py

reports/
└── quality/
    ├── complexity.json
    ├── complexity-summary.json
```

Pythonはレポート集計用途に限定する。

生成レポートは原則としてGit管理対象外とする。

必要に応じてCI Artifactとして保存する。

## 9. 複雑度ランキング

以下の形式で関数単位のランキングを出力する。

```text
KASEIFU / CODE QUALITY

Cyclomatic Complexity

Rank  CC   Function                 File
────────────────────────────────────────────────────
1     18   example_function_a       src/example.rs
2     14   example_function_b       src/example.rs
3      9   example_function_c       src/example.rs

Summary
────────────────────────────────────────────────────
Functions analyzed : 120
CC 1–10            : 110
CC 11–15           :   8
CC 16+             :   2
Maximum CC         :  18
```

数値は表示例であり、実測値ではない。

### 出力要件

- CC降順
- ファイルパス
- 関数名
- 開始行
- CC値
- 閾値判定
- 総関数数
- 最大CC
- 平均CC
- 閾値超過件数

JSON形式でも同じ集計情報を出力する。

---

## 10. 品質管理スクリプト

ローカルで次のコマンドを実行できるようにする。

```bash
bash scripts/quality_check.sh
```

内部で実行する処理：

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets --all-features
```

加えて複雑度解析を実行する。

### 実装要件

- 各検査の終了コードを保持する。
- 失敗した検査を明示する。
- 大量の標準出力を必要以上に表示しない。
- 詳細ログはファイルに保存する。
- 最終的なサマリーを表示する。
- CIからも同じスクリプトを呼び出せる。

Clippyやテストが失敗した場合も、可能な範囲で残りの検査を実行し、最後に結果を集約する。

# Part D — GitHub Actions

## 11. CIの導入

`.github/workflows/rust-quality.yml` を作成する。

### 実行タイミング

- Pull Request
- mainブランチへのPush

### 検査項目

1. rustfmt
2. Clippy
3. cargo test
4. Cyclomatic Complexity
5. Quality Report

### 実行環境

macOS Runnerを使用する。

kaseifuはSpotlightやmacOS固有APIに依存するため、Linux Runnerだけで全テストが動作することを前提にしない。

### CI要件

- Rust toolchainのバージョンを固定する。
- 依存関係をキャッシュする。
- 複雑度解析ツールのバージョンを固定する。
- レポートをArtifactとして保存する。
- 秘密情報をログへ出力しない。
- Jevの実APIキーを通常の品質検査で要求しない。
- 外部API依存テストにはMockを使用する。

# Part E — ベースライン管理

## 12. 初回ベースライン

初回導入時、既存コードの複雑度を測定する。

例：

```text
reports/quality/baseline.json
```

記録項目：

- 解析ツール名・バージョン
- Rust toolchain
- 対象コミット
- 解析対象ファイル
- 関数別CC
- 閾値超過一覧

### 管理方針

- ベースラインはレビュー済みの状態で保存する。
- 既存の超過関数は直ちに失敗扱いにしない。
- 新規関数のCC 16以上はCIで失敗とする。
- 既存関数がCC 16以上へ悪化した場合はCIで失敗とする。
- CC 11〜15は警告として表示する。
- 既存の高CC関数が改善された場合、ベースライン更新を検討する。

### 比較の注意

関数名や行番号だけで関数を同一視すると、移動・改名で誤判定する可能性がある。

関数の識別方法を設計し、比較できない場合は誤って品質悪化と断定しない。

# Part F — テスト・検証

## 13. 必須テスト

### Lint

- 正常なコード
- Clippy警告のあるコード
- フォーマット違反
- 警告抑制の検出

### Complexity

- CC 1の関数
- CC 10の関数
- CC 11の関数
- CC 15の関数
- CC 16の関数
- ネストした条件分岐
- match式
- 非同期関数
- 解析不能なファイル

### Baseline

- 新規関数
- 関数削除
- 関数改名
- 関数移動
- CC改善
- CC悪化
- 解析ツールのバージョン変更

### CI

- 全検査PASS
- Lint失敗
- テスト失敗
- Complexity超過
- 解析ツール実行失敗
- Artifact生成

解析ツールが失敗した場合、複雑度0として扱わない。

## 最終原則

**Lintはコードの問題を検出し、循環的複雑度は構造的な複雑さを定量化する。**

両者を混同せず、別々の指標として管理する。

品質ゲートは、既存コードの全面修正を要求するものではなく、新たな品質悪化を防ぎ、改善を継続するための仕組みとする。

# kaseifu v3.4 追加仕様
## 品質目標値・合格基準（Quality Gates）

### 1. 品質目標一覧

| 指標 | 目標基準 | 警告基準 | CI失敗基準 |
|---|---|---|---|
| rustfmt | 違反0件 | — | 1件以上 |
| Clippy | 警告0件 | — | 1件以上 |
| Cyclomatic Complexity（CC） | 10以下／関数 | 11〜15 | 新規・変更関数で16以上 |
| Cognitive Complexity | 15以下／関数 | 16〜20 | 21以上（将来の品質ゲート候補） |
| 関数のコード行数 | 50行以下 | 51〜100行 | 101行以上（新規・変更関数） |
| ネスト深度 | 3以下 | 4 | 5以上（新規・変更関数） |
| テスト成功率 | 100% | — | 1件でも失敗 |
| テストカバレッジ | 80%以上 | 70〜79% | 70%未満（段階導入） |

**これらはkaseifu独自の品質目標であり、Rust公式の品質基準ではない。**

認知的複雑度、関数行数、ネスト深度、カバレッジについては、実際に採用したツールで計測可能であることを確認してからCI失敗条件を有効化する。

### 2. 循環的複雑度の管理

| CC | 評価 | 対応 |
|---|---|---|
| 1〜5 | Excellent | 推奨 |
| 6〜10 | Good | 合格 |
| 11〜15 | Warning | 改善推奨 |
| 16〜20 | High | 新規・変更関数はCI失敗 |
| 21以上 | Critical | 優先的にリファクタリング |

目標は、**全関数の95%以上をCC 10以下にすること**。

既存コードについては初回計測時にベースラインを保存し、CC 16以上の関数を改善対象として一覧化する。

### 3. プロジェクト全体の品質KPI

| KPI | 初期目標 | 最終目標 |
|---|---|---|
| CC 10以下の関数比率 | 90%以上 | 95%以上 |
| CC 16以上の関数数 | ベースライン以下 | 0件 |
| 最大CC | ベースライン以下 | 15以下 |
| Clippy警告 | 0件 | 0件 |
| rustfmt違反 | 0件 | 0件 |
| テスト成功率 | 100% | 100% |
| テストカバレッジ | 70%以上 | 80%以上 |

カバレッジは `cargo-llvm-cov` などの導入を別途検討する。カバレッジ80%は品質管理上の目標であり、プログラムの正しさを保証する数値ではない。

### 4. CI適用方針

**導入直後**

- rustfmt違反：CI失敗
- Clippy警告：CI失敗（既存警告を解消した後に有効化）
- テスト失敗：CI失敗
- CC 11〜15：警告
- CC 16以上：既存分はベースライン管理、新規・変更関数はCI失敗
- カバレッジ：レポートのみ

**安定運用後**

- 全関数の95%以上がCC 10以下
- CC 16以上の既存関数を段階的に解消
- カバレッジ80%以上を目標
- 新規・変更関数の品質基準を継続適用

```text
Coverage

```

上記数値は表示例であり、実測値ではない。

### 6. 運用上の注意

- 解析ツールのバージョンを固定する。
- 関数のCCとファイル単位のCCを混同しない。
- CC計測不能な関数をCC 0として扱わない。
- 関数の改名・移動による誤判定を避ける。
- CIの品質ゲートを回避するためだけの関数分割を禁止する。
- テストカバレッジだけを上げる無意味なテストを禁止する。
- 品質基準を満たしていても、可読性や設計上の問題があればレビュー対象とする。

## 最終目標

**全関数の95%以上でCC 10以下、Clippy警告0件、rustfmt違反0件、テスト成功率100%、テストカバレッジ80%以上。**

これをkaseifuの継続的なコード品質管理目標とする。
