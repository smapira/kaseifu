# kaseifu — Apple Foundation Models統合・AIリネーム機能 開発指示書 v2.0（完全版）

**実装方式：Rust ↔ Swift FFI（C ABI）**  
**対象：ファイル・画像・動画・フォルダ**  
**設定保存：既存SQLite DB**  
**キャッシュ：追加しない**  
**実行方式：Dry-runデフォルト、Journal / Undo対応**

本指示書は、kaseifuにApple Foundation Modelsを利用したAIリネーム機能を追加するための開発仕様である。

ユーザーが命名ルールを選択し、AIが必要な意味情報を補完する方式を採用する。

既存コードとDBスキーマの最新状態は未確認である。実装前に既存アーキテクチャを調査し、既存機能の再利用を優先すること。

---

# 1. 開発目的

## 1.1 概要

ファイル・フォルダの内容を解析し、整理に適した名前を提案する。

対象には以下を含める。

- 一般文書（PDF、TXT、Markdownなど）
- 画像（JPEG、PNG、HEICなど）
- 動画（MP4、MOVなど）
- フォルダ

単純なAIによる自由命名ではなく、ユーザーが指定した命名ルールに従って名前を生成する。

## 1.2 設計原則

| 原則 | 要件 |
|---|---|
| Native First | macOS標準APIを優先 |
| Rust First | 主処理はRustで実装 |
| Swift Minimal | SwiftはApple APIとの橋渡しを担当 |
| FFI | C ABIによる同一プロセス内呼び出し |
| No Cache | 独自キャッシュを追加しない |
| SQLite Reuse | 既存DBを利用 |
| No New Config Files | 新しいTOML等を作成しない |
| Dry-run First | デフォルトはプレビュー |
| Reversible | 実行したリネームはUndo可能 |
| User Controlled | 命名ルールはユーザーが選択 |
| No Silent Fallback | モデル切替を暗黙に行わない |

# 3. RustとSwiftのFFI接続

## 3.1 接続方式

RustからSwiftのC互換関数を呼び出す。

```text
Rust
 │
 │ extern "C"
 ▼
C ABI
 │
 ▼
Swift
 │
 ▼
Foundation Models
```

外部プロセス、JSON Lines、XPCは使用しない。

## 3.2 FFI API

最低限、以下の機能を提供する。

| API | 目的 |
|---|---|
| `kaseifu_fm_available` | モデル利用可否確認 |
| `kaseifu_fm_create` | 推論コンテキスト生成 |
| `kaseifu_fm_generate` | 意味情報生成 |
| `kaseifu_fm_cancel` | 推論キャンセル |
| `kaseifu_fm_free_result` | 結果メモリ解放 |
| `kaseifu_fm_destroy` | コンテキスト破棄 |

関数名は仮称。既存コードの命名規則を確認して確定する。

## 3.3 非同期処理

Foundation Modelsの推論は非同期である。

FFI境界では、Swiftの非同期処理をRustへ安全に橋渡しする。

推奨方式：

**Swiftで非同期推論を実行し、完了時にRustへコールバックする。**

```text
Rust
 │
 │ generate(request, callback)
 ▼
Swift
 │
 │ Task
 ▼
Foundation Models
 │
 │ await response
 ▼
Swift
 │
 │ callback(result)
 ▼
Rust
```

### 必須要件

- Rustの非同期ランタイムをブロックしない。
- Swiftの非同期処理をC ABI境界へ直接公開しない。
- コールバックの寿命を管理する。
- Rust側の所有権を明確化する。
- Swift側のメモリ解放責任を明確化する。
- SwiftのエラーをFFI境界へ安全に変換する。
- コンテキスト破棄中にコールバックが発生しないよう制御する。
- タイムアウトとキャンセルを実装する。
- 多重完了・二重解放を防止する。

## 3.4 データ交換

初期実装では、FFIの引数・戻り値にJSONを利用する。

これはプロセス間通信ではなく、同一プロセス内のデータ交換である。

### Request

```json
{
  "request_id": "rename-001",
  "target_type": "image",
  "path": "/Users/example/Pictures/IMG_1234.HEIC",
  "language": "ja",
  "analysis": {
    "title": true,
    "category": true,
    "project": false
  }
}
```

### Response

```json
{
  "request_id": "rename-001",
  "status": "success",
  "semantic": {
    "title": "海辺の夕日",
    "category": "風景",
    "project": null
  }
}
```

JSONのスキーマバージョンを管理し、未知フィールドや不正な値を安全に処理すること。

# 4. Apple Foundation Models

## 4.1 利用目的

Foundation Modelsには、ファイル名全体ではなく、命名に必要な意味情報を生成させる。

例：

```json
{
  "title": "プロジェクト提案書",
  "category": "企画",
  "project": "Kaseifu"
}
```

命名規則の適用はRust側で行う。

## 4.2 モデル利用条件

実行時に以下を確認する。

- 対応macOSバージョン
- Apple Intelligence対応環境
- Apple Intelligenceの有効状態
- Foundation Modelsの利用可能状態

利用できない場合は明示的なエラーを返す。

別のLLMへ暗黙にフォールバックしない。

## 4.3 画像対応

Foundation Modelsの画像入力機能を利用する。

画像の内容理解とタイトル生成を行う。

```text
Image
  │
  ▼
Foundation Models
  │
  ├── Image Understanding
  ├── Title Generation
  └── Category Extraction
```

画像入力APIは対応するOS・モデルに依存するため、実装時にApple公式APIの利用条件を確認すること。

## 4.4 動画対応

動画はAVFoundationで代表フレームを抽出し、Foundation Modelsで解析する。

```text
Video
  │
  ▼
AVFoundation
  │
  ├── Duration
  ├── Resolution
  ├── Creation Date
  └── Representative Frames
           │
           ▼
     Foundation Models
           │
           ▼
     Semantic Metadata
```

動画ファイルをFoundation Modelsへ直接入力することは前提としない。

# 5. ファイル種別別の解析仕様

## 5.1 一般文書

対象：

- PDF
- TXT
- Markdown
- HTML
- その他、既存抽出機構が対応する形式

### 処理

```text
Document
   │
   ▼
FileContext
   │
   ├── Filename
   ├── Metadata
   └── Extracted Text
           │
           ▼
    Foundation Models
           │
           ▼
      Semantic Data
```

### 要件

- ファイル全文を無条件に読み込まない。
- 入力トークン数を制限する。
- 文書内の日付を抽出できるようにする。
- 複数の日付が存在する場合は区別する。
- ファイル内の命令文を実行指示として扱わない。

---

## 5.2 画像

対象：

- JPEG
- PNG
- HEIC
- TIFF
- WebPなど、実行環境でデコード可能な形式

### 解析情報

| 情報 | 取得方法 |
|---|---|
| 画像内容 | Foundation Models |
| 撮影日時 | ImageIO / EXIF |
| カメラ機種 | ImageIO / EXIF |
| 解像度 | ImageIO |
| OCR | Vision |
| ファイル作成日時 | Filesystem Metadata |

### 処理

```text
Image
  │
  ├── ImageIO
  │      └── EXIF Metadata
  │
  └── Foundation Models
         └── Image Understanding
                │
                ▼
           Semantic Data
                │
                ▼
          Naming Rule Engine
```

### 生成例

```text
Before:
IMG_1234.HEIC

After:
2026-10-14_海辺の夕日.HEIC
```

### 要件

- 画像のアスペクト比を保持する。
- 必要に応じて入力画像を縮小する。
- 元画像を変更しない。
- 画像内の人物を推測で特定しない。
- 不明確な内容を断定しない。

---

## 5.3 動画

対象：

- MP4
- MOV
- M4V
- その他、AVFoundationが対応する形式

### 解析情報

| 情報 | 取得方法 |
|---|---|
| 再生時間 | AVFoundation |
| 解像度 | AVFoundation |
| フレームレート | AVFoundation |
| 作成日時 | AVFoundation / Filesystem |
| 代表フレーム | AVFoundation |
| 映像内容 | Foundation Modelsによるフレーム解析 |

### 代表フレーム抽出

初期設定：

**3〜5フレームを抽出する。**

例：

```text
Video Duration: 120 seconds

Frame 1:  12s
Frame 2:  36s
Frame 3:  60s
Frame 4:  84s
Frame 5: 108s
```

フレーム抽出位置は動画の長さに応じて調整する。

### 処理

```text
Video
  │
  ▼
AVFoundation
  │
  ├── Metadata
  │
  └── Frame Extraction
          │
          ▼
    Foundation Models
          │
          ▼
    Semantic Data
          │
          ▼
    Naming Rule Engine
```

### 生成例

```text
Before:
VID_0012.MOV

After:
2026-10-14_海辺の風景.MOV
```

### 制限事項

- フレーム解析だけでは音声内容を理解できない。
- 動画全体の動作を正確に理解できるとは限らない。
- 短時間しか映らない重要な場面を見逃す可能性がある。
- 複数画像の同時入力が利用できない環境では、個別フレームを解析して結果を統合する。

---

## 5.4 フォルダ

### 解析対象

- 子ファイル名
- 子フォルダ名
- ファイル種別の分布
- 代表ファイルの内容
- ディレクトリ構造
- 親フォルダ名

### 生成例

```text
Before:
新しいフォルダ/
├── invoice_001.pdf
├── invoice_002.pdf
├── contract.pdf
└── payment.xlsx
```

```text
After:
請求・契約関連書類/
```

### 要件

- 大規模フォルダはサンプリングする。
- 無制限の再帰解析は禁止する。
- 空フォルダは内容ベースの命名を保留する。
- 内容が混在する場合は無理に共通テーマを生成しない。
- フォルダ名変更による子要素のパス変更を考慮する。

# 6. Naming Rule Engine

## 6.1 基本方針

ユーザーが選択した命名ルールをRust側で適用する。

```text
Semantic Data
     │
     ▼
Naming Rule Engine
     │
     ▼
Generated Name
```

## 6.2 初期プリセット

| ID | パターン | テンプレート |
|---|---|---|
| P01 | AI命名 | `{title}` |
| P02 | 日付プレフィックス | `{date}_{title}` |
| P03 | 日付サフィックス | `{title}_{date}` |
| P04 | 固定プレフィックス | `{prefix}_{title}` |
| P05 | 固定サフィックス | `{title}_{suffix}` |
| P06 | カテゴリ＋タイトル | `{category}_{title}` |
| P07 | 日付＋カテゴリ | `{date}_{category}_{title}` |
| P08 | 連番 | `{seq}_{title}` |
| P09 | 日付＋連番 | `{date}_{seq}_{title}` |
| P10 | プロジェクト＋タイトル | `{project}_{title}` |
| P11 | メタデータ命名 | `{date}_{device}_{title}` |
| P12 | カスタム | ユーザー指定 |

## 6.3 テンプレート変数

| 変数 | 説明 |
|---|---|
| `{title}` | AI生成タイトル |
| `{category}` | AI分類カテゴリ |
| `{project}` | プロジェクト |
| `{prefix}` | 固定プレフィックス |
| `{suffix}` | 固定サフィックス |
| `{date}` | 日付 |
| `{time}` | 時刻 |
| `{year}` | 年 |
| `{month}` | 月 |
| `{seq}` | 連番 |
| `{parent}` | 親フォルダ |
| `{device}` | 撮影デバイス |
| `{type}` | ファイル種別 |

## 6.4 日付形式

以下をサポートする。

```text
YYYY-MM-DD
YYYYMMDD
YYYY-MM
YYYY
YYYY年MM月DD日
```

日付取得元：

1. ファイル作成日時
2. ファイル更新日時
3. EXIF撮影日時
4. 文書内の日付
5. 現在日時

文書内の日付はAI抽出値であるため、曖昧な場合はユーザー確認を必要とする。

## 6.5 不足値

テンプレートの必須変数が取得できない場合は、提案を保留する。

不足した値をAIが捏造して補完してはならない。

# 7. SQLite統合

## 7.1 方針

既存SQLite DBを使用する。

新しいDBファイルは作成しない。

新しいTOML、YAML、JSON設定ファイルも作成しない。

## 7.2 保存対象

| データ | 保存 |
|---|---|
| 命名ルール | 必須 |
| ユーザープリセット | 必須 |
| デフォルトルール | 必須 |
| リネーム履歴 | 必須 |
| Undo情報 | 必須 |
| AI推論キャッシュ | 不要 |
| メタデータキャッシュ | 不要 |
| ファイル内容キャッシュ | 不要 |

## 7.3 スキーマ変更

既存DBスキーマを調査する。

既存テーブルで表現可能なら再利用する。

新しいテーブルが必要な場合のみ、マイグレーションを追加する。

# 9. リネームの安全性

## 9.1 必須検証

| 検証項目 | 要件 |
|---|---|
| 空文字 | 禁止 |
| `.` / `..` | 禁止 |
| パス区切り文字 | 禁止 |
| NUL文字 | 禁止 |
| 長すぎる名前 | ファイルシステムの制限を確認 |
| 同名ファイル | 上書き禁止 |
| 拡張子変更 | 原則禁止 |
| シンボリックリンク | 初期実装では対象外 |
| 変更前後が同名 | No-op |
| Unicode | 正規化差異を考慮 |
| 大文字小文字 | ファイルシステム特性を考慮 |

## 9.2 TOCTOU対策

候補生成から実行までの間にファイル状態が変化する可能性がある。

実行直前に以下を再確認する。

- 対象ファイルの同一性
- 移動先の存在
- 親ディレクトリの状態
- アクセス権限

macOSの安全なrename APIを検討する。

`renameatx_np` の `RENAME_EXCL` などを候補として検証する。

## 9.3 Journal

リネーム実行前に操作をJournalへ記録する。

```text
Pending
   │
   ▼
Rename
   │
   ▼
Success
```

失敗時：

```text
Pending
   │
   ▼
Rename Failed
   │
   ▼
Failure
```

プロセス異常終了時の復旧処理も設計する。

# 10. Undo

既存Undo機構へ統合する。

### 要件

- ファイルのリネームを戻せる。
- 画像のリネームを戻せる。
- 動画のリネームを戻せる。
- フォルダのリネームを戻せる。
- 一括リネームを戻せる。
- 変更前の名前を保持する。
- Undo先に別ファイルが存在する場合は上書きしない。
- 二重Undoを防止する。
- 親フォルダのリネーム後も子要素の履歴を解決できる。

# 11. パフォーマンス

## 11.1 基本方針

独自キャッシュは実装しない。

高速化は処理構造の最適化によって実現する。

## 11.2 最適化対象

| 対策 | 内容 |
|---|---|
| FFI | プロセス間通信を排除 |
| Session Reuse | 推論セッションを再利用 |
| Lazy Extraction | 必要な場合だけ内容を抽出 |
| Directory Sampling | フォルダ解析量を制限 |
| Batch Processing | 複数対象を効率的に処理 |
| Metadata First | まずメタデータを利用 |
| Bounded Concurrency | 同時処理数を制限 |
| Early Exit | 解析不能な対象を早期に除外 |

## 11.3 画像最適化

- 入力画像を必要に応じて縮小する。
- 元画像を変更しない。
- EXIFを先に取得する。
- 不要なOCRを実行しない。

## 11.4 動画最適化

- 動画全体をデコードしない。
- 代表フレームだけを抽出する。
- フレーム数に上限を設ける。
- 長時間動画でも処理量を制限する。
- フレーム抽出に失敗した場合は安全にスキップする。

## 11.5 Foundation Modelsセッション

Swift側で推論セッションを管理する。

ただし、セッション再利用によって異なるファイル間で会話履歴が混ざらないようにする。

セッション再利用の効果はベンチマークで評価する。

| ファイル読み取り失敗 | 対象をスキップ |
| 名前衝突 | 実行禁止 |
| 権限不足 | 実行禁止 |
| Journal書き込み失敗 | リネーム禁止 |
| Undo失敗 | 履歴を保持 |
| FFIエラー | 安全にRustへ伝達 |

FFI境界を越えてSwiftの例外やRustのpanicを伝播させないこと。

# 15. 受け入れ基準

以下をすべて満たすこと。

1. RustからSwiftをFFI経由で呼び出せる。
2. Apple Foundation Modelsによる意味情報抽出が動作する。
3. 文書・画像・動画・フォルダをリネームできる。
4. ユーザーが命名ルールを選択できる。
5. 日付・Prefix・Suffix・カテゴリ・連番を利用できる。
6. カスタムテンプレートを利用できる。
7. 命名ルールを既存SQLiteへ保存できる。
8. 新しい設定ファイルを追加しない。
9. 独自キャッシュを追加しない。
10. Dry-runがデフォルトである。
11. 既存ファイルを上書きしない。
12. Journalに操作履歴を記録する。
13. Undoが動作する。
14. 親フォルダのリネーム後も履歴の整合性を維持する。
15. Foundation Modelsが利用できない場合、安全に終了する。
16. FFI境界でメモリリークや未定義動作を起こさない。
17. 既存のorganize / watch機能を破壊しない。

# 16. 最終的な実装方針

kaseifuのAIリネーム機能は、Rustを中心としたネイティブ構成で実装する。

```text
Rust
 ├── FileContext
 ├── Naming Rule Engine
 ├── Rename Planner
 ├── Rename Executor
 ├── SQLite
 └── FFI
      └── Swift
           ├── Apple Foundation Models
           ├── AVFoundation
           ├── ImageIO
           └── Vision（必要時）
```

追加する主要機能は以下の3つ。

**① Foundation Models FFI Bridge**

RustからApple Foundation Modelsを利用するためのSwift実装。画像入力、動画フレーム解析にも対応する。

**② Naming Rule Engine**

ユーザーが選択した命名ルールを適用するRust実装。

**③ Rename Service**

文書・画像・動画・フォルダのリネーム、Dry-run、Journal、Undoを統合するRust実装。

既存のFileContext、SQLite、Journal、Undoは可能な限り再利用する。

**新規設定ファイル、別DB、独自キャッシュ、外部プロセスは導入しない。**

また、将来的に既存の`organize`処理からRename Serviceを呼び出せるよう、リネーム機能をCLIに密結合させず、独立したサービスとして設計する。

これにより、ファイル整理とAIリネームを同一のワークフローへ統合できる構成とする。
