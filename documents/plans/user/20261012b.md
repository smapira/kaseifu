## 1. 開発目的

現行のkaseifuは、Jev APIを利用するために環境変数または `.env` の設定が必要となっている。

これは開発者向けの利用方法であり、一般ユーザー向けCLIとして適切ではない。

本開発では、ユーザーがシェル環境や設定ファイルの内部構造を理解しなくても利用できる設定管理基盤を実装する。

### 最終的なユーザー体験

初回：

```bash
kaseifu setup
```

通常利用：

```bash
kaseifu classify ~/Desktop/example.pdf
```

設定確認：

```bash
kaseifu config show
```

診断：

```bash
kaseifu doctor
```

### 必須原則

1. 一般ユーザーに `.env` の作成を要求しない。
2. `source` や `export` を要求しない。
3. APIキーはmacOS Keychainに保存する。
4. 通常設定はユーザー単位で永続化する。
5. 作業ディレクトリに依存しない。
6. 開発者向け環境変数との互換性を維持する。
7. 既存のJev API、Discovery、Policy、ファイル操作の挙動を変更しない。

# Part A — 設定管理アーキテクチャ

## 3. 設定情報の分類

設定を次の3種類に分離する。

| 分類 | 例 | 保存先 |
|---|---|---|
| 一般設定 | API URL、モデル、動作設定 | TOML |
| 秘密情報 | Jev APIキー | macOS Keychain |
| 一時的な上書き | CI、開発、デバッグ | 環境変数・CLI引数 |

APIキーを通常の設定ファイルに保存してはならない。

### 保存先

ユーザー設定：

```text
~/Library/Application Support/kaseifu/config.toml
```

Keychain：

```text
Service: com.routeflags.kaseifu.jev
Account: default
```

ServiceとAccountは今回提案する識別子である。

実装前に既存の識別子との衝突がないことを確認し、採用後は安易に変更しないこと。

設定パスはハードコードしたホームディレクトリ文字列ではなく、macOSのユーザー領域を適切に解決すること。

---

## 4. 設定ファイル仕様

例：

```toml
[jev]
endpoint = "https://api.typesafe.ai/v1/systemone"
model = "jev-latest"

[classifier.thresholds]
auto_move_confidence = 0.85
auto_move_margin = 0.40
review_confidence = 0.60

[operations]
dry_run = true
enable_undo = true
```

APIキーは含めない。

### 設計要件

- TOML形式を使用する。
- 未指定値にはアプリケーションのデフォルト値を適用する。
- 不正な値はエラーとして報告する。
- 既存の `config/default.toml` をデフォルト値の参照元として活用する。
- 設定ファイルが存在しない場合も、安全なデフォルト値で起動できるようにする。
- ユーザー設定の更新時は一時ファイルを使用し、可能な限り原子的に置換する。
- 不必要に設定全体を書き換えない。

設定スキーマを明確に定義すること。

---

## 5. 設定の優先順位

優先順位は以下とする。

```text
CLI Overrides
      ↓
Environment Variables
      ↓
User Configuration / Keychain
      ↓
Application Defaults
```

### Jev設定の解決

| 設定 | 第一優先 | 通常値 |
|---|---|---|
| Endpoint | CLI / `JEV_API_URL` | ユーザー設定 |
| Model | CLI / `JEV_MODEL` | ユーザー設定 |
| API Key | `JEV_API_KEY` | Keychain |

`JEV_API_BASE_URL` は後方互換のために維持する。

`JEV_API_URL` と `JEV_API_BASE_URL` の両方が設定されている場合は、`JEV_API_URL` を優先する。

既存のJev URL正規化処理を維持し、`/v1/systemone` を二重に付与しないこと。

### 注意事項

CLI引数でAPIキーそのものを指定する仕組みは導入しない。

シェル履歴やプロセス引数に秘密情報が残るためである。

# Part B — CLIコマンド

## 6. `kaseifu setup`

初回設定ウィザードを実装する。

```bash
kaseifu setup
```

### 処理フロー

1. 既存設定を確認する。
2. Jev API URLを表示する。
3. Jevモデルを表示する。
4. APIキーの入力を求める。
5. APIキーをKeychainへ保存する。
6. 一般設定をTOMLへ保存する。
7. 設定状態を確認する。
8. 完了メッセージを表示する。

### UI例

```text
╭─ ◈ KASEIFU / SETUP ───────────────────────────────╮
│                                                   │
│  Welcome to kaseifu                               │
│                                                   │
│  Jev API Endpoint                                 │
│  https://api.typesafe.ai/v1/systemone             │
│                                                   │
│  Model                                            │
│  jev-latest                                       │
│                                                   │
│  API Key                                          │
│  ••••••••••••••••••••••••                         │
│                                                   │
│  ✓ API key saved to macOS Keychain                │
│  ✓ Configuration saved                            │
│                                                   │
│  Setup complete                                   │
│                                                   │
╰───────────────────────────────────────────────────╯
```

### 入力仕様

- APIキー入力時はターミナルへのエコーを無効化する。
- 入力値をログに記録しない。
- 既存設定がある場合は現在値を表示する。
- APIキーは表示せず、登録済みかどうかだけを示す。
- 既存のAPIキーを無断で上書きしない。
- 入力中断時は設定を不完全な状態にしない。
- 非TTY環境では対話入力を開始せず、適切なエラーを返す。

通信テストを実施する場合は、実際にAPIリクエストが発生することを明示する。

認証確認に適切なAPIエンドポイントが存在するか調査すること。

## 7. `kaseifu auth`

認証情報を管理する。

### APIキー登録

```bash
kaseifu auth set-key
```

Keychainへ保存する。

APIキーは対話形式で入力する。

### 認証状態

```bash
kaseifu auth status
```

表示例：

```text
Jev Authentication

Provider       Jev
API Key        Configured
Storage        macOS Keychain
Endpoint       https://api.typesafe.ai/v1/systemone
```

この表示は保存状態の確認であり、通信確認をしていない場合に「認証成功」と表示してはならない。

### APIキー削除

```bash
kaseifu auth remove-key
```

Keychainの該当エントリを削除する。

削除前に確認を求める。

## 8. `kaseifu config`

一般設定の管理コマンドを実装する。

### 表示

```bash
kaseifu config show
```

### 更新

```bash
kaseifu config set jev.model jev-latest
```

```bash
kaseifu config set jev.endpoint https://api.typesafe.ai/v1/systemone
```

### 仕様

- 設定キーを検証する。
- 型を検証する。
- 未知のキーを拒否する。
- APIキーを `config set` で登録できないようにする。
- 保存前に値を検証する。
- 更新に失敗した場合は既存設定を維持する。
- APIキーなどの秘密情報を表示しない。

## 11. JevIntegrationの変更

現在の `RealJevIntegration::from_env()` に直接依存する構成を改善する。

推奨：

```rust
struct JevConfig {
    endpoint: String,
    model: String,
    api_key: SecretString,
}
```

`SecretString` は概念的な型名であり、採用するクレートの仕様に合わせること。

### 新しい処理フロー

```text
CLI
 │
 ▼
Configuration Resolver
 ├─ CLI Options
 ├─ Environment
 ├─ User TOML
 ├─ Keychain
 └─ Defaults
 │
 ▼
Resolved JevConfig
 │
 ▼
RealJevIntegration
 │
 ▼
Jev API
```

設定解決とAPI通信を分離する。

Jevアダプター自身が作業ディレクトリ内の `.env` を探索する設計にはしない。

### 後方互換性

- 既存の環境変数を維持する。
- 既存テストが利用する依存性注入を維持する。
- `from_env()` の扱いは既存呼び出し元を確認して決定する。
- 開発・CI環境での利用を破壊しない。

# Part E — セキュリティ

## 13. 必須セキュリティ要件

- APIキーを平文設定ファイルへ保存しない。
- APIキーをstdout/stderrへ出力しない。
- APIキーをデバッグログに含めない。
- APIキーをシェル引数として受け取らない。
- Keychain操作失敗時に安全に停止する。
- Keychainが利用できない場合、平文保存へ自動的にフォールバックしない。
- 認証失敗と設定不足を区別する。
- APIキーの値を含むエラーを返さない。
- 設定ファイルを更新する際に既存設定を破壊しない。

### APIキーの取り扱い

Keychainに保存する際は、サービス識別子とアカウント識別子を固定する。

取得時には現在ユーザーのKeychainを利用する。

必要に応じてmacOSの認証ダイアログが表示されることを想定する。

## 最終設計原則

**一般ユーザーには設定の複雑さを見せない。**

- 認証情報はKeychain
- 一般設定はTOML
- 開発者向けの一時設定は環境変数
- 初回設定は `kaseifu setup`
- 日常操作は `kaseifu classify` / `organize`

kaseifuを、開発者向けの実験的CLIから、一般ユーザーが継続利用できるmacOSアプリケーションへ発展させる。
