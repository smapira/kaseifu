# plan-architect 検討: AIリネーム P8（`20261015d-ai-rename-p8.md`）

本ラウンドは親スレッドが計画と実装を直接行った（委任2回が書き込み前に停止）。ここには設計時に実際に比較した論点と、却下した理由を残す。

## 確定した判断（比較した選択肢つき）

| 論点 | 採用 | 却下した選択肢と理由 |
|---|---|---|
| 起動形 | `rename <folder> --recursive` | 複数位置引数（原典に無い / 管理フラグとの衝突規則が増える）、ディレクトリの既定を一括にする（Phase 7 の意味を壊す） |
| プレビューの形 | サマリのみパネル、項目は素の行、矢印は `->` | 全行パネル（狭い端末で折り返す。実測）、矢印を原典どおり非 ASCII で出す（出力 ASCII の規約違反） |
| 衝突の単位 | 集合（同一ディレクトリ + 小文字化した名前）で保留 | トポロジカルに並べて連鎖を成功させる（実行順の正しさを名前に依存させる）、警告だけで通す（原典 §9.1違反） |
| 大文字小文字 | 小文字化して畳む（APFS は既定で同一視） | ASCII のみの比較（日本語やアクセント付きの大小を取り逃す） |
| Unicode 正規化 | ここでは畳まない。適用時の再確認が原因になる | 正規化表の導入（新規 crate が要る = 禁止） |
| 変更の入口 | `--execute` + TTY かつ非 JSON のときだけ `[y/N]`、`--yes` で省略 | 常に確認（非 TTY でハング）、JSON でも確認（2文書になる） |
| 深さと件数 | 深さ3 + 50件 + `bounded:` の明示 | 無制限（原典 §5.4 違反）、片方だけの制限（深い/広いのどちらかで破綻） |
| 適用順序 | 深い順（子が先） | プレビュー順（子の plan が必ず1件失敗）、包含のある組を保留（ツリー一括の主用途を拒否する） |
| 一括 Undo | 既存 `undo --last N` + 結果に `undo:` 行 | journal にバッチ id 列（スキーマ移行）、`operation` の変更（既存 undo が拾わなくなる） |
| モデル不可 | ウォーク後、対象があるときだけ1回確認して安全終了 | 対象ごとに同じ失敗を繰り返す、unavailable を held として続行 |
| 並行度 | 逐次（同時1） | 固定本数の並列（セッションの取り合いが計測できず、失敗の再現性が落ちる）。Phase 9 の計測対象 |
| ラウンド分割 | 分割しない | プレビュー + 衝突 + 実行 + 一括 Undo は互いに依存する（一括 Undo の意味は「1件 = 1行」の実行方式で決まり、衝突検出は実行対象の集合で決まる） |

## 実装前に確認した事実（推測で設計しないため）

- `undo` の選択条件が `operation = 'move'` を含むため、一括の行も `move` のままにする必要がある。
- 連鎖（`a -> b` と `b -> c`）は、**既存の「宛先が存在すれば保留」が先に効く**ため2件同時に Ready にならない。したがって集合の衝突検出は「同じ名前を提案した2件」に絞れる。
- 非 TTY の確認は `handle_organize_select` が先例（作業前に拒否 + `--yes`）。rename はフォルダ内の対象を自動で選ぶので、選択の拒否ではなく確認の省略として扱うのが自然だと判断した。

## 実装中に計画を修正した点

- `plan` / `apply` を `main.rs` から `src/rename/batch.rs` へ移した（fake provider で検証するため。計画時は CLI 層に置く想定だった）。
- `BatchPhase` を導入（プレビューと「確認待ち」と結果で表示を分ける。実機で `dry-run` の表示が誤っているのを検出）。
- 空フォルダではモデルを要求しない（対象0件なら確認の意味がない）。
