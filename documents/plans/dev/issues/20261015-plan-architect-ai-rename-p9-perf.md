# plan-architect 検討: AIリネーム P9（`20261015e-ai-rename-p9-perf.md`）

親スレッドが計画と実装を直接行った。設計時に比較した論点と却下理由を残す。

## 論点と結論

| 論点 | 採用 | 却下と理由 |
|---|---|---|
| セッション再利用の扱い | 既定 off の opt-in として実装し、測定して採用しないと決める | 実装しない（§11.5 の評価ができない）、既定 on（効果が測れずリスクだけ残る） |
| 再利用の粒度 | 指示文ごとに 1 セッション | ターゲット種別ごと（指示文は結局 4 種あり、種別だけでは決まらない） |
| 測定の場所 | `kaseifu-bench perf`（既存の研究バイナリ） | `kaseifu` 本体（ユーザーの help とワークフローを汚す）、ドキュメントのみ（第三者に再現不能） |
| 再利用の有効化経路 | 既存の `kaseifu_fm_create(options_json)` を使う（すでに JSON を受けて無視していた） | 新しい C ABI の追加（ABI 面を増やす必要がない） |
| メモリ測定 | `getrusage` の `ru_maxrss`（自プロセス）+ `/usr/bin/time -l`（CLI 全体） | 外部プロファイラ（権限が要る）、推測値 |
| 異常終了の検証方法 | 計画中 kill の実測 + 記録/成否間の状態を直接作って復旧挙動を確認 | 1 ms 未満の窓を狙っての kill（再現性がない） |
| 長尺動画の素材 | 開発時に一時生成（`/tmp`、105 KB）し `--video` で測定 | リポジトリへの大素材追加（フィクスチャは数 KB を保つ方針）、ffmpeg（本機で動かない） |
| レポート形式 | min/median/mean/max を常に出す | 平均のみ（ばらつきが大きいため誤読を招く） |

## 実装前に確認した事実

- 現行経路は**1 生成ごとに `LanguageModelSession` と `FmContext` を作る**（`SwiftFmBridge::generate`）。つまり再利用の比較対象は「生成ごとのコンテキスト + セッション生成」である。
- `kaseifu_fm_create(options_json)` は options を検証するだけで使っていなかった。オプションは後方互換に追加できる。
- `libc` は既存依存なので `getrusage` に新しい crate は要らない。
- 「計画後にソースが消える」等の失敗は Phase 8 の適用順序と再確認で既に扱われている（本ラウンドはそれを再測定しただけ）。

## 計画を修正した点

- 当初は「セッション生成コストだけ」を測る ABI を考えたが、**同じワークロードを再利用の有無で 2 回走らせる**方が製品経路に忠実で、ABI を増やさないためこちらにした。
- `--generations` を増やす必要があると分かった（n=3 では差がばらつきに埋もれる）。計画時の既定を n=3 から実行時に上げて両方記録するようにした。
- 履歴混入の検出は「語」だけでなく「1 番目のファイル名」も見るようにした（音写が多いため）。
