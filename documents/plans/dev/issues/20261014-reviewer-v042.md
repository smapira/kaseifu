## 敵対的検証（実測・コード）

1. **構文の実在性**: 採用したクエリ形で `mdfind -count` が終了コード 0（3545）。ASCII 外の語（日本語 `画像`）や記号入りの語（`c#1`）を含む形も終了コード 0 を実測 → クエリ言語として有効
2. **切り捨て位置の反証**: スタブで「無関係 100 件 → 写真フォルダ 3 件」を返すと、修正前の `take(50)` では写真が消えるが、修正後は写真フォルダが D1（`v042_candidates_beyond_the_old_hit_window_still_rank`）
3. **PDF 回帰の実機再確認**: `D1 = ~/OS/…/State Of Mind Labs / score 1.0 / reasons 完全一致`（17 件の候補集合・順位も before/after で同一）
4. **既存テストとの整合（M1）**: phase4 系（PNG ターゲット `CBX（…）とは？｜NATURECAN.png`）は X:CBX がファイル名に含まれるためスコープ付きクエリでも `*CBX*` 条件が残り、スタブ `query.contains("CBX")` が成立。260 passed / 0 failed（phase4_context / phase4_full_pipeline とも緑）→ 実装は空振りしていない（候補 2 件の断言が通っているため非空虚）
5. **決定的クエリ**: 同一入力で 2 回キャプチャして完全一致（`v042_image_query_is_deterministic`）。語はソート + dedup
6. **メタ文字**: `it's` のようなクエリを壊す語は条件から除外（`v042_image_query_skips_terms_with_query_metacharacters`）。全語が除外された場合は従来の語クエリへフォールバック（`v042_image_without_name_terms_falls_back_to_the_word_query`）
7. **上限超の候補**: 70 ディレクトリを返しても上位 50 件のみがランキング順で返る（`v042_candidate_destinations_are_capped_after_ranking`）
8. **プライバシー**: クエリ・reason に撮影日時/座標は一切含まれない（変更はファイル名語のみ。`reasons` は既存項目のまま）
9. **型ノイズ除外**: `kMDItemKind` 由来の `image` を条件に入れるとシステム/アプリ領域が 288 件増えることを実測済み（Q8）。除外はノイズ削減として合理的
10. **残余（非ブロッキング）**: `~/Pictures/Eagle.library/images/<hash>.info` のようなアプリ内画像ストアが名前類似度で上位に来る（1 写真 = 1 ディレクトリのため）。これは「写真を含むディレクトリ」であり、パス除外は本リクエストのスコープ外として記録（M3）

## 性能（debug ビルド・同一マシン・5 回計測）

| 写真 `discover --all`（cold 除く） | 0.22–0.24s / max RSS 34.0–34.5 MB | 0.93–0.97s / max RSS 18.3–19.3 MB |

- `mdfind` 子プロセスの最大 RSS は語クエリ 34.1 MB / 属性スコープクエリ 8.3 MB（実測）。`/usr/bin/time -l` の値は子プロセス支配のため、修正後の RSS が下がるのはこの差
- Rust 側の増分は 3.5k の `SimilarFile`（各 ~200B）と集約マップで数 MB 未満（上限 10k でも ~1MB のパス + 数 MB）→ 上限の根拠として妥当
- 体感への影響: 写真 1 件の discovery が +0.7s。`classify` は対話操作なので許容範囲（計測値を計画書 §T5 に記録）
