## 4. 設計判断（選択肢と結論）

### D1. ジャーナル上のリネーム表現: 既存 `move` 行を再利用する

- 選択肢A（採用）: 同一ディレクトリ内移動として `operation='move'` で記録（source=旧パス、destination=新パス）。`candidate_id` にパターン ID（例 `P02`）、confidence/margin は NULL（AI の確信度では無いため捏造しない）。
- 選択肢B（不採用）: 新 `operation='rename'` を追加。`last_successful_move`（`history.rs:166-181`）・undo・doctor の条件すべてに分岐が要り、混在履歴の順序保証の検証コストが高い。
- 根拠: undo（`undo.rs:38-46`）は source/destination だけを見て逆向き rename するため同一 dir の move 行はそのまま戻せる。doctor は行数・pending のみを見るため不変。「rename 実行 → `undo --last 1` で旧名復帰 → 二重 undo 停止」の実測で示す。
- 将来 Phase 7/8 で区別が必要になれば `operation` 値の拡張を再検討する（本ラウンドでは行わない）。

### D2. 新 `rename` サブコマンドの CLI 形状: フラットな `Rename` バリアント＋管理系フラグ

- 選択肢A（採用）: `Commands::Rename { target: Option<PathBuf>, --execute/--dry-run, --pattern, --template, --prefix/--suffix/--project/--seq/--date-format, --preset, --patterns, --save-preset NAME, --delete-preset NAME, --list-presets, --set-default ID, --show-default }`。`organize`（`main.rs:95-112`）と同一流儀。`--pattern` は ID（`P01`〜`P12`、大文字小文字不問）と slug の両方を受け付ける（plan-architect 指摘 A1。slug 対応: P01 `ai`, P02 `date-title`, P03 `title-date`, P04 `prefix-title`, P05 `title-suffix`, P06 `category-title`, P07 `date-category-title`, P08 `seq-title`, P09 `date-seq-title`, P10 `project-title`, P11 `meta`, P12 `custom`。P12 は `--template` 必須）。`--select` とは無関係（rename に選択 UI は無いためフラグ自体を生やさない）。
- 選択肢B（不採用・原典の字面どおり）: `kaseifu rename patterns` のような位置引数サブコマンド。clap derive では位置引数 `document.pdf` とサブコマンド名 `patterns` が衝突し（未知サブコマンドはエラーで位置引数へフォールバックしない）、`./patterns` という実ファイルとの曖昧性も生む。`rename document.pdf`（原典 §8.1 の基本形）を壊す。
- 結論: 原典 §8.6 の `rename patterns` は `rename --patterns` に読み替える（本計画書での宣言をもって仕様確定とし、help 文に明記する）。`--execute` 無しは dry-run（原典 §8.1）。`--execute --dry-run` 併用は `organize` 同様 conflict エラー。bare `rename`（target 無し・管理フラグ無し）はガイダンス表示（exit 0、無副作用）。
- `emit_report`（`main.rs:1103-1119`）に乗せる。`--format json` は新規キー追加のみ（既存キーは触らない。形状固定: `{"rename": {"target", "current_name", "proposal"|null, "status": "proposed|executed|noop|held|error", "reason"|null, "pattern", "date_source", "operation_id"|null}}`。plan-architect 指摘 A4）。

### D3. 可視コマンド自動走査テストと zsh 補完

- `tests/completion_test.rs:192-213` は `--help` から可視コマンドを抽出するため `rename` は自動で検査対象に入る。zsh スクリプトは clap_complete が CLI 木から生成するため `src/completion/` への手書き追加は不要。ただし「`rename` が help と zsh スクリプトの両方に現れること」「`discover` が漏れないこと」を新規 `v092` テストでも二重化して実測する。

### D4. プリセット保存・変更・削除の CLI 形状と SQLite スキーマ

- CLI: `--patterns`（P01〜P12 一覧＋保存済みプリセット一覧）、`--preset NAME`（保存済みプリセットを使用）、`--save-preset NAME`（今回の `--template`/`--pattern` 等の解決結果を NAME で保存・上書き）、`--delete-preset NAME`（削除。存在しなければエラー）、`--list-presets`（保存済みのみ一覧）。デフォルトルールは `rename --set-default <pattern-id|preset-name>` / `rename --show-default` で扱う。
- スキーマ（同 DB `kaseifu.db`、新規ファイルなし。`history.rs:86-104` と同一 `CREATE TABLE IF NOT EXISTS` パターンだが、`history.rs` 自体は変更せず新 `src/rename/store.rs` の `RenameStore::open(path)` が自表のみ確保する。plan-architect 指摘 A2。CLI は journal と同一パス（`history::journal_path()`）を開く）:
  - `rename_presets (name TEXT PRIMARY KEY, template TEXT NOT NULL, date_format TEXT NOT NULL DEFAULT 'YYYY-MM-DD', created_at TEXT NOT NULL, updated_at TEXT NOT NULL)`。CHECK 制約で空文字禁止。
  - `rename_settings (key TEXT PRIMARY KEY, value TEXT NOT NULL)`。`key='default_rule'` に `P01`〜`P12` の ID または `preset:<name>` を格納。
- ビルトイン P01〜P12 はコード定数（DB に seed しない。seed するとユーザー削除との区別・マイグレーション順序の問題が生じる）。`--patterns` 表示時にビルトイン＋保存済みを結合する。
- 代替案（不採用）: 新 TOML/JSON 設定ファイル・別 DB・`config.toml` 慣習への相乗り。原典 §7 が SQLite 指定であり原典を優先する。`config` コマンド配下にも置かない。

### D5. 文書入力の上限・切り詰め・日付解決

- 対象拡張子: `txt` / `md`（`markdown` 含む）/ `pdf` / `html`（`htm` 含む）。大文字小文字不問。対象外拡張子は明示エラー（Phase 5/6/7 の守備範囲と理由を添える）。拡張子なし・不明はエラー（推測しない）。
- 上限: ファイル読み取りは先頭 `32_768` バイト（32 KiB）まで。Rust 側でテキスト抜粋を最大 12 件×120 文字の `T:` 信号に切り詰める（契約の 20 件×120 文字、`contract.rs:30-33`、および Swift プロンプト上限 2000 文字に収めるため）。切り詰め時は捏造に見える接尾辞を足さず件数で打ち切る。全文を読まない（原典 §5.1）。
- 形式別の読み方（新規 crate なし）: txt/md/html はバイト上限で切り出して UTF-8 lossy 変換（html はタグを空白化する最小処理。`<>` 単純走査のみ。レンダリング・外部パーサなし。plan-architect 指摘 A5）。pdf はバイナリのため印字可能断片を順に拾う最小スキャン（復号・展開はしない。スキャン不能なら信号ゼロで続行）。読めない部分は空として扱い、捏造しない。
- 入力パイプライン（plan-architect 指摘 A3）: `context::builder::build` → `normalize::normalize` → `semantic_signals` 末尾に文書 `T:` 信号（最大 12 件）を追加 → `SemanticProvider::analyze`。自前の context 手組みはしない。symlink 判定は builder の canonicalize 吸収前にサービス側で `symlink_metadata` により先行実施する。
- 日付解決の優先順位（原典 §6.4）: 作成日時 → 更新日時 → EXIF（文書では通常無し。`image_metadata.capture_time` があれば使う）→ 文書内日付 → 現在日時。文書内日付は Rust 側の正規表現スキャン（`YYYY-MM-DD` / `YYYYMMDD` / `YYYY/MM/DD` 等の明確な形式のみ。複数ヒット・相対日付は「曖昧」として不採用）。原典は「文書内の日付は AI 抽出値」と言うが、契約・Swift 無変更で確定的に実装するため Rust 抽出に読み替える（AI に日付を捏造させない §6.5 と整合。曖昧時の「ユーザー確認」は dry-run 表示の `date_source` 開示＋ `--execute` による明示実行で代替する）。使用した取得元は出力に必ず表示する。
- 日付形式 5 種: `YYYY-MM-DD` / `YYYYMMDD` / `YYYY-MM` / `YYYY` / `YYYY年MM月DD日`（非 ASCII は生成名のみに許容。CLI 罫線・ラベルは ASCII のまま）。

### D6. テンプレート解決と必須変数保留（原典 §6.5）

- 変数 13 種: `{title}` `{category}` `{project}` `{prefix}` `{suffix}` `{date}` `{time}` `{year}` `{month}` `{seq}` `{parent}` `{device}` `{type}`。未知変数はエラー（黙って空にしない）。`{seq}` は CLI `--seq N`（既定 1、0 埋め 3 桁 `001`）。`{device}` は文書では通常空 → 含むテンプレート（P11）は文書では保留（捏造しない）。`{type}` は拡張子小文字。`{parent}` は親ディレクトリ名。`{time}` は `HH-MM-SS`（`:` を避ける）。
- 必須変数が空なら提案を保留し、理由（`missing: device` 等）を出力する。AI に再生成させて埋めない。空 title も保留。
- 拡張子は変更しない（新名の拡張子 == 旧拡張子でなければエラー。「原則禁止」を厳格側に倒す。Phase 4 の安全優先）。

### D7. 名前検証（原典 §9.1）と TOCTOU

- 検証順: 空文字 → `.`/`..` → `/`・NUL（`\\` と `:` も拒否）→ 長さ（UTF-8 で 255 バイト超は拒否）→ 拡張子同一 → シンボリックリンク（`symlink_metadata` で判定。対象外エラー）→ 変更前後同名（バイト一致で No-op。unicode-normalization crate が無いため完全 NFC 比較は不可と宣言し残リスクに記録。`to_lowercase` 一致は衝突検査に委ねる）→ 同名（移動先 exists → 上書き禁止エラー）→ 親ディレクトリ存在・is_dir → 書き込み権限（readonly 事前拒否。最終保証では無い旨を注記）。
- TOCTOU: 実行直前に同一性（exists/is_file/サイズ・mtime 再取得。変化で中止）・移動先不存在・親 dir・権限を再確認して即 `rename`。`renameatx_np` の `RENAME_EXCL` は検討したが採用しない（libc 0.2 の macOS シンボル保証が未確認・条件付き分岐が複雑化する。`std::fs::rename`＋直前再確認で実装し、残る微小ウィンドウを残リスクに記録する）。
- Journal: 検証通過後に `record_pending("move", ...)` → `rename` → `mark_success`/`mark_failure`（`mover.rs` と同一順序）。dry-run は journal 無書き込み（`mover::dry_run` と同原則）。

## 5. BDD シナリオ（振る舞いと具体例）

### Phase 3: Naming Rule Engine

- R1 ビルトイン全解決: semantic `{title: "プロジェクト提案書", category: "企画", project: "Kaseifu"}`、date `2026-10-14`、parent `Documents`、seq `3`、prefix `WORK`、suffix `v2`、device 空、type `pdf` に対し、P01→`プロジェクト提案書`、P02→`2026-10-14_プロジェクト提案書`、P03→`プロジェクト提案書_2026-10-14`、P04→`WORK_プロジェクト提案書`、P05→`プロジェクト提案書_v2`、P06→`企画_プロジェクト提案書`、P07→`2026-10-14_企画_プロジェクト提案書`、P08→`003_プロジェクト提案書`、P09→`2026-10-14_003_プロジェクト提案書`、P10→`Kaseifu_プロジェクト提案書`、P11→保留（`missing: device`）、カスタム `{year}{month}_{title}`→`202610_プロジェクト提案書`。
- R2 日付形式: `2026-10-14` に対し `YYYY-MM-DD`→`2026-10-14`、`YYYYMMDD`→`20261014`、`YYYY-MM`→`2026-10`、`YYYY`→`2026`、`YYYY年MM月DD日`→`2026年10月14日`。不正形式名はエラー。
- R3 日付優先順位: creation 有り→creation。以降 creation 無し→modified、両方無し→document 日付、すべて無し→now（`date_source` を返す）。document 日付が複数・曖昧→不採用で now へ。
- R4 必須変数保留: `{project}` 空で P10→保留（`missing: project`）。`{title}` 空→全パターン保留。AI に埋めさせない。
- R5 未知変数: `{unknown}` を含むテンプレート→エラー（空置換しない）。
- R6 プリセット永続化: `--save-preset memo --template "{date}_{title}"` → 再プロセスで `--preset memo` が解決できる。空名・空テンプレートは拒否。上書きは更新として明示表示。`--delete-preset memo` → 以降 `--preset memo` はエラー。デフォルト未設定時の `--show-default` は `P02`（出荷既定）を表示する。
- R7 SQLite 方式: `kaseifu.db` 単一ファイル。`operations` 表は不変。新表のみ追加。

### Phase 4: Document Rename

- D1 dry-run 既定: `rename note.txt`（title=`会議メモ` 取得）→ 移動せず提案表示。journal 行数不変。FS 変更なし。
- D2 execute: `rename note.txt --execute` → `success` 行が 1 行増える（`operation='move'`）。`undo --last 1` で旧名に復帰し、二重 undo は停止する。
- D3 形式: PDF/TXT/MD/HTML が対象。`.jpg` は Phase 5 守備範囲エラー。拡張子なしはエラー。大文字拡張子は小文字化比較で判定する。
- D4 入力上限: 100 KiB の txt → 先頭 32 KiB のみ読み、`T:` 信号は最大 12 件。巨大 PDF でもクラッシュなし。空ファイル → 信号ゼロで継続する。
